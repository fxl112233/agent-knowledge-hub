# AgentKnowledgeHub 高频面试问题清单

> 适用场景：秋招项目面、AI 应用开发、RAG / Agent 工程岗位。
> 本文以“面试官最可能怎么问”为主，不展开背诵式答案。参考回答见 [interview-guide.md](interview-guide.md)，实验依据见 [benchmark-report.md](benchmark-report.md)。

## 使用方法

- **P0**：必须能够脱稿回答，并能结合代码或实验数据说明。
- **P1**：高概率追问，需要讲清设计取舍、失败场景和替代方案。
- **P2**：系统设计或深入技术面中可能出现。
- 回答顺序建议统一为：**业务问题 → 方案选择 → 数据流 → 取舍 → 实验或测试证据**。
- 不要把检索指标说成回答准确率，也不要使用尚未实测的“千级文档”“提升 95%”等数字。

答案状态说明：

- **已实现**：代码中存在真实链路，并有自动测试或运行记录。
- **部分实现**：主路径存在，但仍有明确的工程缺口。
- **实测**：答案引用仓库当前固定实验结果。
- **生产方案**：面向未来上线的设计回答，不能说成当前系统已经具备。

## 一、最可能被问到的 20 个问题

1. **请用 1 分钟介绍这个项目，你独立完成了什么？最难的部分是什么？**

   **回答（已实现）：** 我独立完成的是 Python 版企业文档知识管理 MVP。系统把解析、抽取、问答和更新划分为 4 个职责 Agent，用 LangGraph 编排 ingest、qa、update 三条流程；数据层使用 SQLite、Chroma、Neo4j 和 Kafka。最难的不是接一个模型 API，而是让多格式解析、稳定 Chunk、跨模态检索、图谱来源、引用校验和增量更新形成同一套可恢复的数据契约。如果重做，我会先把跨存储事务日志和异步任务系统打牢，再扩展模型能力。

2. **为什么要做 Multi-Agent，普通 RAG 链不够吗？为什么正好拆成 4 个 Agent？**

   **回答（已实现）：** 我不是因为步骤多就拆 Agent，而是按输入输出契约、工具依赖、失败补偿和扩缩容边界来拆。解析、知识抽取、问答、知识更新四类任务差异足够大；校验、分块、RRF、哈希 Diff 等小步骤仍是普通节点。继续细拆会增加状态传递、调用成本和错误传播，所以 4 个是当前工程边界，不是理论上的固定最优数。

3. **4 个 Agent 分别负责什么？哪些会调用 LLM？**

   **回答（已实现）：** 文档解析 Agent 负责格式解析、OCR、可选视觉描述和分块；知识抽取 Agent 用 LLM 提取实体、关系和事件；问答 Agent 用 LLM 做 QueryPlan、答案生成和时间事实抽取；知识更新 Agent 主要做 Kafka、幂等、重试和调用入库链路，本身是确定性控制逻辑。更新若产生新增 Chunk，会间接触发抽取 LLM；不是四个 Agent 每次都调用生成模型。

4. **三条 LangGraph 流水线的数据怎么流转，条件边在哪里？**

   **回答（已实现）：** 入库图传递 `IngestState` 和 `IngestTransaction`，在 diff 后按 unchanged/embed 分支，任一阶段错误进入 rollback。问答图传递 `QAState`，Vector 与 Graph 两路从 plan 后并发汇合，再按无证据、时间、计算或普通回答分支。更新图传递 `CDCEvent/UpdateResult`，先做幂等和 delete/upsert 路由，一致性失败进入一次 repair。三种状态都是 TypedDict，trace 只记录阶段、路由、重试和错误类型。

5. **Supervisor 是 LLM 自主规划还是确定性路由？如何避免循环和踢皮球？**

   **回答（已实现）：** Supervisor 不是自由规划器，只接受 `ingest/qa/update` 三个白名单值并转到对应子图。子图是固定 DAG，Agent 没有任意互调接口，重试次数也有上限，因此不会靠自然语言互相转交任务。这样牺牲了一部分自主性，但企业知识入库和更新更需要可预测、可审计和可恢复。

6. **一次问题从 API 到答案的完整链路是什么？哪些步骤并行？**

   **回答（已实现）：** `/api/qa/ask` 校验请求后生成 QueryPlan；Vector 与 Graph 候选检索并发执行；Hybrid 使用加权 RRF；之后做文档级 Rerank、选中文档内二次检索、Chunk 级 Rerank和证据打包；再路由到时间工具、受限计算校验、普通生成或拒答；最后只保留能映射到真实召回 Chunk 的引用。Hybrid 中单路失败可以使用另一路，双路失败才视为致命错误。

7. **为什么同时使用向量检索和知识图谱？什么时候图检索会变差？**

   **回答（实测）：** 向量检索擅长语义相似，图检索补实体关系和跨文档路径。在固定 100 题中，Hybrid 的 All-evidence Hit@10 比 Vector 高 5.34 个百分点，说明图候选确实补到了一些多跳证据。但实体抽取错误、关系只是共现、实体过泛或跳数过大时，图扩展会引入噪声，所以项目限制 1–3 跳、使用参数化查询、词法相关度和自适应图权重。

8. **Hybrid 为什么使用加权 RRF？公式是什么？**

   **回答（已实现）：** Chroma 返回距离或相似度，Neo4j 返回基于实体匹配和跳数的启发式分数，两者不在同一标尺上，不能直接相加。项目使用 `score(d)=Σ weight_i/(60+rank_i(d))`，默认 Vector 权重 1.0、Graph 基础权重 0.85，并根据问题和图候选质量调整图权重。RRF 只依赖各路排名，降低异构分数校准问题。

9. **Reranker 和文档内二次检索解决什么问题？会重复生成查询向量吗？**

   **回答（已实现）：** 初召回追求 Recall，容易把同一文档的相似段落或弱相关段落带入上下文。项目先对最多 40 个候选做文档筛选，再在最多 10 篇候选文档内用已有文本/VL 查询向量二次检索，最后做 Chunk 精排和每文档最多两个 Chunk 的多样性控制。查询向量会复用，不再产生额外 Embedding 调用；Rerank 失败则回退到 RRF 排名。

10. **如何保证答案引用真实可追溯？**

    **回答（已实现）：** 生成模型只能返回本次上下文中的 `chunk_id`。QAAgent 会用召回上下文构建白名单，过滤不存在的 ID；回答声称可回答但没有合法 citation 时强制改为不可回答。Citation 返回 doc_id、chunk_id、页码或工作表、quote、模态和检索类型；时间工具同样验证两侧引用。当前 quote 是 Chunk 前 300 字符，不是更细粒度的句级 span，这是后续可改进点。

11. **MultiHop-RAG 怎么用？为什么是 Recall@10，是不是每题有 10 篇标准文档？**

    **回答（实测）：** `@10` 表示系统返回前 10 个候选，不表示标准答案有 10 篇文档。MultiHop-RAG 的问题通常需要 2–4 篇跨文档证据；Evidence Recall 计算找回的标准证据比例，All-evidence Hit 要求全部标准证据都出现在 Top10。本轮为控制成本使用固定 100 篇语料子集和固定 100 题配对问答，不等于完整数据集或真实企业线上流量。

12. **当前实验结果说明了什么？为什么检索变好但 Answer EM 下降？**

    **回答（实测）：** Vector/Hybrid 的 Evidence Recall@10 是 74.44%/76.78%，All-evidence Hit@10 是 45.33%/50.67%，但 Answer EM 是 60.00%/57.33%。这说明图增强改善了找齐证据的能力，却没有稳定传递到生成端；主要问题包括新增噪声、证据打包和通用 ComparisonTool 过度拒答。配对 EM 差值的 95% CI 是 `[-10.67, 5.33]` 个百分点，所以我只陈述检索提升，不宣称问答准确率提升，并默认关闭了收益为负的 ComparisonTool。

13. **为什么分块使用约 350 token、50 overlap，并增加 900/100 的父块？如何调参？**

    **回答（已实现，效果待完整消融）：** 我先按页、章节、工作表等来源单元切分，再用 350/50 的子块做检索，以提高实体、日期和局部事实的定位精度；同时保存 900/100 的父块，精排时拼接父块和前后一个子块，避免小块切断语义。最终 citation 仍绑定原始子块，不把扩展上下文伪装成引用。这个参数不是普适最优，仍应在固定集上比较多组 size/overlap 的 Recall、All-evidence Hit、索引成本和延迟。

14. **11 类文档如何统一成可检索结构？**

    **回答（已实现）：** 各解析器先输出 `ParsedUnit(content, unit_id, metadata)`，再统一变成 `DocumentChunk`。公共字段有 doc_id、chunk_id、内容哈希、版本、模态和来源；格式专有元数据保留 page、section、slide、sheet、row_start/end、JSONPath、XPath、asset_path 等。这样向量库、图谱、目录库和引用层不需要理解每种原始格式。

15. **“真多模态”与只嵌入 OCR 文本有什么区别？失败如何降级？**

    **回答（已实现并真实预检）：** 图片不只产生 OCR 文本和视觉描述，还把受管原始图片送入 `Qwen/Qwen3-VL-Embedding-8B`，进入独立 `knowledge_image_v2` 集合；文本查询也生成同一 VL 空间的查询向量，因此可以文本查图。真实预检中图片和文本向量都是 1024 维。视觉描述失败会保留 OCR 并记录 fallback；但如果 VL Embedding 本身失败，当前入库阶段会失败回滚，还没有把它降级为“只写 OCR 文本向量”。

16. **Neo4j 中实体、关系、Chunk 和来源如何建模？**

    **回答（已实现）：** `Chunk` 保存内容、文档、版本和来源；`Entity` 用规范化小写名称 key 做唯一约束；`MENTIONED_IN {source_chunk_id}` 把实体绑定到原文；业务关系统一为 `RELATION {predicate, confidence, source_chunk_id}`。不把 LLM 输出直接拼成动态关系类型，是为了保持 Schema 可控、避免 Cypher 注入和关系类型爆炸。

17. **文档更新时如何做到增量？chunk_id 为什么稳定？**

    **回答（已实现）：** Chunk ID 由 `doc_id + 来源单元 unit_id + 规范化内容哈希 + 同单元重复序号` 做 SHA-256 截断。重新解析后相同来源单元和内容保持相同 ID，再用新旧 ID 集合得到 added、removed、unchanged；只对 added 做 Embedding和抽取，只删除 removed。当前数据结构没有单独的 changed 集合，内容变化会表现为旧 ID removed、新 ID added。

18. **SQLite、Chroma、Neo4j 没有分布式事务，如何保证一致性？**

    **回答（部分实现）：** 当前采用幂等 upsert/delete、SQLite 事件状态、跨存储 Chunk ID 校验、失败补偿和 repair/rebuild，而不是伪装成强事务。CDC 事件最多尝试 3 次，只有成功后才提交 Kafka offset。需要坦诚的是，入库图当前先写 SQLite commit 再 verify，验证失败会标记文档 FAILED 并删除本次新增向量/图记录，但不能完整恢复旧目录快照；生产版应引入事务日志、staging 版本或 outbox/saga 后再原子切换可见版本。

19. **1000 页 PDF 如何处理？**

    **回答（生产方案）：** 当前配置把 PDF 限制为最多 500 页，同步上传接口没有实测 1000 页，因此不能说已经支持。生产版会把上传与处理拆开：原文件进对象存储，创建异步任务，按页解析/OCR、分批写入、页级进度和失败重试；检索使用文档—章节—Chunk 层级和文档内二次检索。用户可以在达到可查询水位后增量开放，而不是让 HTTP 阻塞到全部完成。

20. **这个项目算 Toy 还是生产系统？**

    **回答（实际边界）：** 它不是只有 notebook 和单文件脚本的 Toy，因为有真实存储、三条工作流、Kafka 幂等、恢复、上传安全、126 项测试、87.94% 覆盖率和可复现实验。但它仍是可运行 MVP，不是已承载真实企业流量的生产系统；缺少认证授权、多租户、对象存储、分布式任务、高可用、灾备、SLO 监控和规模压测。面试中我会称它为“具备生产化设计意识的工程 MVP”。

## 二、架构与 Multi-Agent

1. 为什么不使用一个“大 Agent”完成解析、抽取、问答和更新？

   **回答（已实现）：** 这四类任务的输入、工具、失败处理和资源需求不同。一个大 Agent 会把文件解析错误、模型结构化错误、在线问答延迟和 CDC 一致性混在同一上下文里，难以测试和恢复；拆分后仍由类型化状态和统一 Ingestion/GraphRAG 服务共享数据契约。

2. 4 个 Agent 的划分依据是业务能力、模型能力，还是数据所有权？

   **回答（已实现）：** 主要依据是业务能力和失败边界，其次是工具与资源边界，不是按模型数量划分。解析拥有文件和 OCR 工具，抽取拥有结构化 LLM 调用，问答拥有检索与生成，更新拥有事件和一致性状态；数据本身由 SQLite、Chroma、Neo4j 共享管理。

3. Agent 之间传递的是自然语言消息，还是类型化状态？为什么？

   **回答（已实现）：** 传递的是 `IngestState`、`QAState`、`UpdateState` 等 TypedDict，以及 Pydantic/dataclass 对象，不是自由自然语言。这样节点字段、错误和 trace 可验证，减少上下文丢失，也便于 Checkpoint 恢复和单元测试。

4. 哪些决策交给 LLM，哪些决策必须由确定性代码完成？

   **回答（已实现）：** 语义理解类任务交给 LLM，包括视觉描述、实体关系抽取、查询规划、答案生成和时间证据事实抽取；安全与一致性类任务由代码完成，包括文件校验、OCR 触发、分块、哈希 Diff、RRF、日期比较、计算表达式校验、引用白名单和幂等状态机。

5. 知识抽取 Agent 与文档解析 Agent 为什么需要分开？

   **回答（已实现）：** 解析输出的是可复现的结构化 Chunk，抽取输入是 Chunk 并调用付费 LLM。分开后解析可以独立测试、缓存和重跑，模型或 Prompt 升级时只重做抽取；图片视觉描述是解析侧的可选增强，但实体关系仍由抽取 Agent 统一处理。

6. 知识更新 Agent 与文档入库流程有多少逻辑复用？如何避免两套代码行为不一致？

   **回答（已实现）：** 更新 Agent 不复制解析、Embedding 和图写入逻辑，而是调用同一个 `IngestionService.ingest/delete/repair_consistency`。API 上传、重建和 CDC 都经过这套服务，因此稳定 ID、Diff 和跨存储删除保持一致；`cdc_processor.py` 也只保留兼容别名，不再维护第二套实现。

7. Multi-Agent 在这个项目中带来了哪些实际收益，又增加了哪些复杂度？

   **回答（实际判断）：** 收益是职责、状态、重试和观测边界更清楚，入库、在线问答、更新可以独立演进；代价是图状态更复杂、Checkpoint 线程 ID 需要管理、错误可能跨节点传播，而且有些流程节点目前仍只是对统一服务的编排包装。这个项目证明了工程组织收益，但没有做“单 Agent 对 4-Agent”的量化对照，不能声称准确率收益来自 Agent 数量。

8. Agent 拆分到什么粒度会出现收益递减？如何判断应该合并？

   **回答：** 如果两个节点使用同一状态、同一工具、总是串行出现、没有独立重试或扩缩容价值，继续拆分只会增加序列化和调度成本，应合并为普通函数或同一服务。当前 QA 图中 doc rerank/refine/chunk rerank 的实现集中在统一检索服务，就是为了避免在多个 Agent 间复制候选状态。

9. 如果一个 Agent 输出错误，会如何影响后续 Agent？系统在哪些位置做校验？

   **回答（已实现）：** 解析失败返回明确异常，不会把错误文本入库；抽取经过 Pydantic 校验和重试；查询计划无效会使用 fallback plan；Reranker 校验返回索引和分数；生成引用只接受真实 Chunk ID。仍存在语义正确性无法靠 Schema 完全保证的问题，所以需要固定评测和人工失败分析。

10. 两个 Agent 对同一事实给出矛盾结果时，以谁为准？

    **回答（已实现）：** 不采用 Agent 投票。Vector 和 Graph 只是候选来源，最终以原始 Chunk、RRF/Rerank 排序和引用校验为准；时间题要求两侧真实引用，日期先后由代码比较。若文档本身互相冲突，当前应返回不可确定，而生产版还需要文档权威级别和生效版本治理。

11. 这个系统属于协作型多 Agent，还是带自主规划能力的 Agent 系统？为什么？

    **回答：** 更准确地说是“多 Agent 职责边界 + 确定性工作流编排”。QueryPlan 有有限语义规划，但 Supervisor 不让模型自由决定下一位 Agent 或动态生成任务，因此不属于高度自主的开放式 Agent 系统；这是为了企业数据流程的可控性。

12. 如果去掉 LangGraph，只使用普通 Python 函数编排，损失了什么？

    **回答：** 核心业务仍能运行，但会损失统一的类型化状态流、条件边可视化、阶段级 trace、SQLite Checkpoint 和按 thread_id 恢复能力。反过来，如果流程很短且不需要恢复，普通函数更简单，所以 LangGraph 的价值主要在三条长流程，而不是给每个函数套节点。

## 三、LangGraph 三条流水线

### 3.1 文档入库流程

1. `validate → parse → diff → embed → extract → graph_upsert → commit → verify` 中，每一步的输入输出是什么？

   **回答（已实现）：** validate 创建包含 doc_id、文件哈希、旧 Chunk 和下一版本的 `IngestTransaction`；parse 产生新 Chunk；diff 填充 added/removed/unchanged；embed 写新增向量；extract 产生带 source_chunk_id 的实体关系；graph_upsert 写 Chunk 和图谱；delete_removed 删除消失数据；commit 写 SQLite 目录和结果；verify 对比三处 Chunk ID。严格说完整图还包含 `delete_removed` 和失败 `rollback`。

2. 为什么先做 diff，再做 embedding 和知识抽取？

   **回答（已实现）：** Embedding 和 LLM 抽取是入库中最贵的步骤，先用稳定 ID 做集合差分，可以让未变化 Chunk 不再调用外部 API，也保留旧向量和图谱来源。整个文件哈希未变化时更早直接返回 `UNCHANGED`。

3. 同一文件重复上传时如何路由到 unchanged，如何避免再次付费调用模型？

   **回答（已实现）：** `validate_stage` 根据 doc_id 或受管路径找到目录记录，若 SHA-256 与 READY 版本一致且不是 force，就构造 `unchanged_result`；LangGraph 的 diff 条件边直接走 commit，不进入 embed、extract 和 graph_upsert，因此不会新增 Embedding 或抽取调用。

4. Embedding 成功但 Neo4j 写入失败时，状态如何恢复？

   **回答（部分实现）：** 节点会最多尝试两次；仍失败时 rollback 删除本次 `added_ids` 在 Chroma 和 Neo4j 中的记录，保留旧目录 Chunk，并把文档标记 FAILED。由于各存储没有事务，这属于补偿式恢复；如果故障发生在删除旧 Chunk 或目录已提交之后，仍要依赖 repair/rebuild，生产版应增加 staging 版本和事务日志。

5. 为什么版本号只能在全部步骤成功后提交？

   **回答（当前缺口）：** 设计上只有跨存储一致后才应让新版本可见，否则读请求可能看到半完成状态。但当前代码的 `commit_stage` 在 `verify_stage` 前写入 SQLite 的新版本，verify 失败后会标记 FAILED，却不能恢复完整旧目录快照。我会把这点当成生产化改造项：先写 staging/version manifest，verify 后原子切换 active_version。

6. 入库中的“部分失败”如何定义，是否允许单张图片失败但整份文档成功？

   **回答（已实现）：** 视觉描述失败属于可降级错误：保留 OCR，记录 `vision_fallbacks` 和 `partial_failures`，不使整份文档失败；DOCX/PPTX 个别无法解码的内嵌图片目前也会跳过。文本解析、结构安全校验、Embedding、知识抽取或存储失败属于主链路失败，会回滚并返回错误。

7. Checkpointer 保存了什么？服务重启后从哪个节点恢复？

   **回答（部分实现）：** 应用使用 `AsyncSqliteSaver` 保存 LangGraph 每个 thread_id 的状态和节点进度；ingest 使用 `ingest:{doc_id}`，CDC 使用 `cdc:{event_id}`，QA 每次生成新 ID。相同 thread_id 可以利用检查点继续，但当前 API 没有公开“恢复某次任务”的接口，也没有对进程中断场景做生产级任务调度和专项压测。

### 3.2 智能问答流程

1. QueryPlan 包含哪些字段？为什么需要 evidence slots？

   **回答（已实现）：** 包含 intent、最多 3 条 queries、最多 10 个 entities、needs_calculation、answer_type、最多 3 个 evidence_slots 和 target_relation。evidence slot 把比较或时间题拆成 left/right 等必需证据，精排和最终打包会优先覆盖每个必需槽位，避免 Top-K 全被单侧证据占满。

2. 向量召回与图召回如何并行，何时只走单路检索？

   **回答（已实现）：** LangGraph 从 plan 同时连到 `vector_retrieve` 和 `graph_retrieve`，两者到 `rrf_fuse` 汇合；`mode=vector` 跳过图，`mode=graph` 跳过向量，Hybrid 才启用两路。Hybrid 单路异常时 trace 记录 fallback 并继续，只有两路都失败才终止。

3. 为什么先 RRF 融合，再做文档级 Rerank 和文档内二次检索？

   **回答（已实现）：** RRF 先保留多路召回的排名信号，Reranker 再用问题语义筛文档，二次检索负责在选中文档内找更精确段落。这样比直接对全库所有 Chunk 做昂贵精排更可控，也避免 Reranker 完全覆盖图/向量召回信号；精排排名与基础排名还会再次做 RRF 融合。

4. 数值题、时间题、普通问答和拒答分别如何路由？

   **回答（已实现但有边界）：** 无上下文走 abstain；target_relation 非 none 走 TemporalTool；needs_calculation 经过 calculator 节点再生成；其他走普通 answer。当前 calculator 节点本身只标记路由，真正的 `safe_calculate` 用来验证模型返回的算式，并没有独立完成“从证据抽数到确定性答案”的完整工具链。

5. 时间工具为什么使用确定性日期比较，而不是完全交给 LLM？

   **回答（已实现）：** LLM 只负责从两侧引用中结构化抽取主体、主张和日期；代码解析年月日并比较 before/after/same_time，再根据问题目标关系输出 Yes/No。这样把容易验证的比较交给程序，同时保留 claim 是否变化这类语义判断给模型。

6. `answerable=false` 的判断依据是什么？阈值如何确定？

   **回答（已实现）：** 当前不是单一分数阈值：无上下文、模型结构化输出失败、布尔答案不满足 Yes/No、没有合法 citation、时间题缺少任一槽位或日期冲突都会拒答。`evidence_score` 是引用得分均值，不是概率，也没有用它直接判定 answerable；生产上线前需要在业务负样本上校准阈值和误答成本。

7. Citation 校验失败时是重试生成、删除引用，还是直接拒答？

   **回答（已实现）：** `_generate` 对无效 JSON 最多按配置重试；生成完成后过滤不在本次上下文中的 ID。如果声称可回答但过滤后没有 citation，直接改为不可回答，不会伪造或静默补引用。LangGraph 最后一层也再次检查 answerable 且 citations 为空的情况。

8. trace 为什么只记录阶段和错误类型，而不返回模型思维链？

   **回答（已实现）：** trace 用于工程观测，记录候选数、路由、耗时阶段、重试和 fallback；这些信息可审计又不依赖模型私有推理。返回思维链既不稳定，也可能泄露 Prompt、文档和敏感信息，所以 API 只提供高层执行轨迹。

### 3.3 增量更新流程

1. Watchdog、管理 API、Kafka 消费者分别承担什么职责？

   **回答（已实现）：** Watchdog 把文件创建/修改/删除转换成事件；管理 API 只允许根据目录中已有 doc_id 产生 update/delete 事件；二者发布到 Kafka。消费者使用固定 consumer group 拉取事件并执行 update LangGraph，成功后才同步提交 offset。

2. 为什么文件监听需要 2 秒去抖？

   **回答（已实现）：** 编辑器保存一次文件可能触发多次 modified，Office 也可能先写临时文件再替换。按绝对路径记录最近时间并在 2 秒窗口内忽略重复通知，可以减少重复事件；它不替代 event_id 幂等，只是生产端降噪。

3. event_id 和幂等键如何设计？同一事件消费两次会发生什么？

   **回答（已实现）：** 每个逻辑事件创建 UUID event_id，并作为 Kafka key 和 SQLite events 主键。消费者发现状态 COMMITTED 就直接返回 duplicate；APPLYING 事件也不能被再次 claim；失败事件在 attempts 未到 3 次时可重试，因此至少一次投递不会重复产生最终写入。

4. `PENDING → APPLYING → COMMITTED/FAILED` 状态机解决了什么问题？

   **回答（已实现）：** PENDING 表示已落目录等待发布/消费，APPLYING 通过 SQLite 原子状态转换抢占，COMMITTED 用于去重，FAILED 保留错误和尝试次数以便重试。启动后还可以把长时间停留在 APPLYING 的事件恢复成 FAILED；不过当前没有完整的后台死信队列管理界面。

5. 文档删除时，如何同步清理三个 Chroma 集合、Neo4j 来源关系和受管图片资产？

   **回答（已实现）：** `IngestionService.delete` 按 doc_id 删除 legacy 和三个 v2 集合中的向量，Neo4j 先删除该文档 Chunk 对应的来源关系和 Chunk，再清理无来源且无关系的孤立实体；随后删除 SQLite 文档记录和文档级资产目录。API 最后只删除精确匹配 `uploads/{doc_id}` 的受管上传目录。

6. 一致性校验失败后，修复命令如何确定哪个存储是基准？

   **回答（已实现）：** 当前以 SQLite catalog 中 READY 文档的 Chunk ID 集合为期望状态，对比 Chroma 与 Neo4j。发现差异就根据 catalog 保存的原文件路径执行 force rebuild；删除事件则清空两端。这个基准依赖原文件仍存在，生产版应把不可变原件放对象存储并保存内容版本 manifest。

7. 为什么本项目的 CDC 不是 Debezium / 数据库 Binlog CDC？

   **回答：** 本项目的变化源是企业文档文件和管理 API，不是业务数据库表，所以使用 Watchdog/API + Kafka 更直接。它是文档事件驱动的增量更新，不能把它描述成数据库 Binlog CDC；若未来接入结构化业务库，才会增加 Debezium connector 和表到知识模型的映射。

## 四、RAG、GraphRAG 与检索

1. RAG 为什么能够缓解幻觉？为什么不能从根本上消除幻觉？

   **回答：** RAG 把生成约束到可更新的外部证据，并让答案引用真实 Chunk，降低仅凭参数记忆编造的概率。但召回可能漏、文档可能错、分块可能切断关系、模型也可能误读，因此它只能降低幻觉风险，不能提供逻辑上的正确性保证。

2. 什么情况下 RAG 会拉低回答效果？

   **回答：** 问题本来是通用常识却注入大量近似文档、库中有过期冲突版本、Top-K 太大、表格线性化错误、图扩展引入泛实体邻居时，额外上下文会稀释注意力。当前 100 题中 Hybrid 检索改善但 EM 下降，就是需要分层定位而不能默认“更多证据一定更好”的例子。

3. 长上下文模型会不会取代 RAG？两者能力边界是什么？

   **回答：** 不会完全取代。长上下文适合少量文档的一次性整体分析；RAG 适合语料持续变化、权限过滤、跨大量文档、控制 token 成本和需要引用的场景。生产中更合理的组合是先检索文档/章节，再把较长的局部上下文交给模型。

4. 垂直领域问答中，什么时候选 RAG，什么时候选微调？

   **回答：** 知识经常变化、必须引用企业事实时优先 RAG；要稳定改变输出格式、语气、工具调用行为或任务模式时考虑微调。企业制度和项目资料属于外部知识，所以本项目先做 RAG；以后可以微调行为，但事实仍由检索提供。

5. Dense Retrieval、BM25、图检索各自适合什么问题？项目如何融合三者？

   **回答（已实现，新增策略效果待完整评测）：** Dense 擅长语义改写，SQLite FTS5/BM25 擅长产品编号、人名、错误码等精确词，图检索擅长显式实体关系和多跳路径。项目先把 Dense 与 BM25 按排名做 Weighted RRF，再把文本混合候选与 Graph 候选做第二层 RRF；不同后端的原始分数不会直接相加。BM25 不可用时会使用确定性词法 fallback，单路失败不阻断回答。

6. 向量检索中的相似度高，是否等于证据正确？

   **回答：** 不等于。相似度只表示向量空间接近，可能是同主题但不回答问题，也可能命中过期版本或反例。因此项目还做文档过滤、Rerank、证据槽位、版本元数据和引用校验；真正正确性仍要结合标准答案或人工审查。

7. GraphRAG 的 1–3 跳范围为什么不能无限扩大？

   **回答（已实现）：** 跳数增加会导致邻居组合爆炸，延迟和噪声快速上升。项目按意图选择 1/2/3 跳，并限制 frontier 和总返回数；实体事实通常 1 跳，比较/分析 2 跳，探索类最多 3 跳。

8. 图路径中的节点和关系如何映射回可引用的原始 Chunk？

   **回答（已实现）：** Entity 通过 `MENTIONED_IN {source_chunk_id}` 连接 Chunk，业务 RELATION 也保存 source_chunk_id。图搜索先扩展实体，再返回这些实体提及的 Chunk 内容、doc_id、page/sheet 和模态，因此最终引用的是原文 Chunk，而不是只引用一个图节点名称。

9. 为什么禁止执行 LLM 任意生成的 Cypher？参数化图查询如何实现？

   **回答（已实现）：** 自由 Cypher 可能读全图、做写操作、注入条件或产生不可控慢查询。项目的查询模板由代码固定，实体 key、document_ids、limit 都作为参数传入，跳数只由程序在 1–3 的白名单内控制；LLM 只输出实体与意图，不输出可执行查询。

10. RRF 中 `k` 的作用是什么？文本、表格、图片权重如何设置？

    **回答（已实现）：** `k=60` 平滑头部排名，防止第一名相对后续候选权重过于极端。模态内融合默认文本 1.0、表格 0.95、图片 0.90，Vector/Graph 默认 1.0/0.85；这些是工程初值而不是已证明最优，应该通过固定集做网格或贝叶斯调参并报告置信区间。

11. Reranker 为什么能够改善初召回结果？它可能在哪些题型上失效？

    **回答（已实现）：** BGE Reranker 联合编码 query 和候选，比独立向量相似度更能判断细粒度相关性。它在日期否定、跨两篇文档组合、超长表格或问题槽位拆错时仍可能失效，所以项目对每个必需 slot 分别精排，并把精排排名与基础 RRF 排名再次融合而不是完全覆盖。

12. 文档级筛选后再做文档内二次检索，可能漏掉哪些证据？如何控制候选文档数？

    **回答：** 如果第一阶段把某个低分但必要的桥接文档淘汰，后续无法找回，这是级联检索的固有风险。当前最多选择 10 篇文档，并用 evidence slots 和图候选提高桥接文档进入率；该参数需要在 Recall、延迟和 Rerank 成本之间做消融。

13. 每篇文档最多保留两个 Chunk 的多样性约束有什么利弊？

    **回答（已实现）：** 好处是避免某一篇长文档占满 Top-K，给跨文档证据留位置；坏处是单篇文档确实需要三个以上远距离段落时会丢信息。当前默认两块，检索层另有图融合阶段的文档约束，后续可根据题型和槽位动态调整。

14. Query Rewrite 为什么可能改变原问题语义？如何检测和回退？

    **回答（部分实现）：** LLM 可能漏掉否定词、主体或时间条件。代码通过 Pydantic 限制最多三条查询和 evidence slots，JSON 失败时回退到原问题启发式计划；但目前没有独立的语义等价模型或规则校验，因此固定 QueryPlan 缓存和失败样本人工检查仍很重要。

15. 无答案问题如何设置负样本，避免系统总是强行回答？

    **回答（已实现评测）：** 评测集中保留标记为 unanswerable 的问题，系统在无上下文、缺槽位、非法引用等情况返回 answerable=false，并用 Rejection F1 评估。负样本不能只做随机无关问题，还应包括相似但缺关键事实、过期版本冲突和权限不可见；后两类尚未进入当前公开数据实验。

## 五、评测与实验结果

1. 为什么选择 MultiHop-RAG，而不是自己生成一批问答对？

   **回答（实测）：** 公开数据集有固定语料、问题、答案和跨文档证据，可复现也便于和其他方法比较；自己让 LLM 生成问题容易与模型偏好同源，形成“自问自答”。但 MultiHop-RAG 主要是公开新闻语料，不代表企业权限、制度版本和表格场景，所以只能作为一层证据。

2. 公开数据集与真实企业线上问题之间仍有哪些分布差异？

   **回答：** 企业问题更短、更口语化，常有缩写、部门权限、历史版本、内部实体、表格指标和多轮指代；公开集的问题通常更完整，证据标注也更干净。上线后还要增加脱敏真实日志、权限负样本、版本冲突、长文档和用户追问集，公开集不能替代线上回归集。

3. 当前固定 100 题是如何抽样的？是否存在用开发集反复调参导致的数据泄漏？

   **回答（实际边界）：** 评测使用 seed=42 的固定分层样本，覆盖比较、推断、时间和无答案，并让 Vector/Hybrid 共用问题和 QueryPlan。100 题被用于多轮开发门控，确实不能再当完全未见测试集；因此结果只作为项目工程实验，若对外做严肃结论应冻结策略后在剩余保留集或新数据上复验。

4. Ground Truth 是文档级还是 Chunk 级？解析后如何把标准证据映射到 Chunk？

   **回答（实测）：** MultiHop-RAG 的标准证据主要是来源文档，当前核心检索指标按 doc_id 计算；入库时保留文档来源和 Chunk 映射，召回的 Chunk 再聚合成文档集合与 expected_doc_ids 比较。Citation 指标也以引用 doc_id 对标准证据文档计算，不代表已有人标注到精确句子 span。

5. Recall@10、Precision@10、All-evidence Hit@10 分别怎么计算？

   **回答：** 设 Top10 去重文档集合为 R，标准证据集合为 G。Recall 是 `|R∩G|/|G|`，Precision 是 `|R∩G|/|R|`，All-evidence Hit 是 `G⊆R` 时为 1，否则为 0；最后对问题取平均。多跳场景不能只看 Recall，因为找回一半证据可能仍无法回答。

6. 为什么 `@10` 表示返回前 10 个结果，而不是每题有 10 个正确证据？

   **回答：** 信息检索指标中的 `@K` 一直表示只考察排名前 K 个结果。MultiHop-RAG 每题通常只有 2–4 篇必要文档，Top10 是给系统的候选预算；K 太小对多跳题过严，K 太大会掩盖噪声并增加生成成本。

7. Answer EM、Token F1、Citation Recall、Rejection F1 分别衡量什么？

   **回答（已实现）：** EM 对标准化后的预测和标准答案做完全相等；Token F1 根据中英文 token 多重集重叠计算精确率/召回率调和平均；Citation Recall 是引用命中的标准证据比例；Rejection F1 把“系统拒答”视为正类，与无答案标签比较。它们分别覆盖严格答案、部分重叠、来源完整性和拒答能力。

8. 对自然语言答案使用 EM 会不会过严？什么情况下必须加入人工评审？

   **回答：** 会，尤其开放式解释可能语义正确但措辞不同，所以 EM 应与 Token F1、规则数值匹配和引用指标一起看。法律财务高风险、开放式答案、模型裁判与规则冲突、策略差异很小、出现新错误类型或准备对外展示案例时，必须人工复核。

9. LLM-as-a-Judge 是否可靠？怎样做盲评、标定和一致性检查？

   **回答（实际方案）：** 它没有固定“准确率”，会受裁判模型、Prompt、领域和答案位置影响。使用前应抽一批人工双标数据，隐藏策略名称和答案顺序，计算裁判与人工的一致率及 Cohen's kappa，再对所有分歧和随机样本复核。当前正式数字主要来自规则指标，不依赖 LLM 裁判。

10. 为什么 Vector 和 Hybrid 必须共用 QueryPlan、Reranker 和生成模型？

    **回答（实测设计）：** 否则两个实验同时改变了问题改写、精排或生成器，差异不能归因于 Graph 分支。当前配对实验固定问题、样本、Top-K、QueryPlan、模型和输出契约，主要变量是是否加入图候选及融合。

11. 配对 Bootstrap 95% 置信区间为什么比只看平均值更可信？

    **回答（已实现）：** Vector 和 Hybrid 回答的是同一批问题，应该按题计算差值，再对题目成对重采样；这样保留问题难度相关性。区间若跨 0，说明当前样本下正负变化都合理，不能只凭平均提升下显著结论；本项目 EM 差值区间就跨 0。

12. 当前 Vector All-evidence Hit@10 为 45.33%，Hybrid 为 50.67%，能得出什么结论，不能得出什么结论？

    **回答（实测）：** 可以说在这批固定样本和配置下，Hybrid 找齐全部标准证据的比例提高 5.34 个百分点，图分支有补充召回价值。不能说回答准确率提高 5.34 个百分点，也不能外推到真实企业流量、完整 MultiHop-RAG 或统计显著的普遍提升。

13. 当前 Hybrid Answer EM 为 57.33%，低于 Vector 的 60.00%，可能原因有哪些？

    **回答（实测分析）：** 新增图候选可能带来同主题噪声；Rerank 和证据打包未必把新增正确文档放进最终生成上下文；QueryPlan 槽位可能拆错；通用 ComparisonTool 对证据要求过严导致拒答。实验后我默认关闭了 ComparisonTool，但还没有在同一固定 100 题上重新证明新默认策略的 EM 提升。

14. 检索更好但回答更差，是生成器问题、上下文噪声，还是指标问题？如何做消融实验定位？

    **回答：** 不能靠猜。我会固定检索结果，用 gold evidence 与实际 evidence 分别生成以判断生成上限；再比较 RRF、+Rerank、+文档内检索、+工具的逐层结果，并按“已找齐证据/未找齐证据”分桶看 EM。若 gold evidence 仍答错是生成或指标问题，若新增候选后答错则偏向上下文噪声和打包问题。

15. 为什么不能把 All-evidence Hit@10 的 50.67% 写成“问答准确率 50.67%”？

    **回答：** 它只判断标准证据文档是否全部出现在 Top10，不检查最终答案内容。回答准确率应使用 Answer EM、Token F1 或经标定的人工/模型评分；当前 Hybrid Answer EM 是 57.33%，两者含义完全不同。

16. 如何分别评测分块、召回、融合、精排、生成和引用校验，避免只看端到端总分？

    **回答：** 分块看文本 F1、OCR CER、表格单元格 F1和稳定 ID；召回看 Vector/Graph 各自 Recall；融合看 RRF 前后 All-evidence Hit；精排看候选 MRR/Recall 保留；生成在固定证据上看 EM/F1；引用看 Precision/Recall 和非法 ID 拒绝。端到端再汇总延迟、成本和错误率。

17. 如果需要证明 GraphRAG 有价值，最小但可信的对照实验应该怎么设计？

    **回答：** 固定同一批多跳问题、解析结果、Embedding、QueryPlan、Reranker、Top-K 和生成器，只比较 Vector 与 Vector+Graph；同时报告检索、回答和引用指标及配对置信区间。再按实体多跳题与非图题分层，至少补一个 Graph-only 诊断，避免平均值掩盖图适用边界。

18. 延迟指标为何要拆成 retrieval、rerank、generation 和 total？

    **回答（已实现）：** total 变慢可能来自外部 LLM，也可能是图查询或精排；不拆分就无法优化和定义 SLA。响应和评测记录 retrieval、generation、total，检索结果内部另有 planning、embedding、rerank 时间；生产版还应增加排队和首 token 延迟。

19. API 调用失败、超时和 fallback 样本是否应该从评测中删除？为什么？

    **回答：** 不应该为了提高分数删除，因为失败率本身就是系统质量。记录要保留 error、重试和 fallback，并同时报告全量业务结果和成功子集诊断；断点续跑只避免重复计费，不能改样本 ID 或跳过困难题。

20. 实验没有达到预期时，如何写在简历上而不夸大？

    **回答：** 写实际完成的工程和明确指标，例如“建立配对评测和 bootstrap CI；Hybrid All-evidence Hit@10 从 45.33% 提升至 50.67%；发现检索增益未传递到 EM并回滚收益为负的比较工具”。不写“准确率 94%”“F1 提升 22%”或没有显著性支持的回答提升。

## 六、多格式与多模态文档

1. 11 类格式具体指哪些格式族？为什么 PNG/JPG 算作一类图片格式？

   **回答（已实现）：** 格式族是 PDF、Word、Excel、CSV、图片、文本、Markdown、PowerPoint、HTML、JSON、XML；扩展名包括 png/jpg/jpeg、html/htm、json/jsonl 等。图片共享同一 OCR、视觉和 VL Embedding 管道，所以按能力族而不是扩展名数量统计。

2. 不同解析器输出如何统一为 Chunk Schema？

   **回答（已实现）：** 每种解析器先输出 ParsedUnit，再由 `_chunk_units` 统一生成 DocumentChunk，包含内容、doc_id、chunk_id、doc_type、content_hash、chunk_index 和 metadata。格式差异被保留在 metadata，而下游只依赖公共字段和 modality。

3. PDF 是如何区分数字文本页与扫描页的？OCR 触发条件是什么？

   **回答（已实现）：** PyMuPDF 先提取页文本，少于默认 40 个字符就把页面按 2 倍分辨率渲染为图片，执行 Tesseract `chi_sim+eng --psm 6`，并选择比原文本更长的 OCR 结果。低文本页还会保存资产并尝试视觉描述；这只是启发式，不是版面分类模型。

4. DOCX、PPTX 中的内嵌图片如何提取、去重和管理生命周期？

   **回答（已实现）：** 解析器从 relationship 或 picture shape 读取二进制，用 PIL 规范化为 PNG，以内容 SHA-256 命名并放到 doc_id 子目录，因此相同图片不会重复写文件。每次成功提交会 prune 不再引用的资产，删除文档时清理整个受管目录。

5. XLSX/CSV 如何保留表头、行列坐标和工作表信息？

   **回答（部分实现）：** XLSX 使用 read_only/data_only 读取，每 20 行形成一个表格单元，metadata 保留 sheet、row_start、row_end；CSV 同样按 20 行分组并保留行范围。内容用 `|` 线性化，首行通常自然作为表头，但当前没有显式 header 字段或单元格列坐标，README 对“完整单元格坐标”的表述应谨慎。

6. HTML 为什么禁止加载远程资源？如何防止 SSRF？

   **回答（已实现）：** 使用本地 `HTMLParser` 只处理上传文件中的标题、正文和表格，不发起网络请求，也不会跟随 img/script/link。没有远程资源抓取入口，就从设计上缩小 SSRF 面；生产仍应在网络层限制解析 Worker 出网。

7. JSON/JSONL 为什么要保留 JSONPath？深度和节点数如何限制？

   **回答（已实现）：** JSONPath 能让引用定位到具体字段，而不是只指向整个文件。解析使用显式栈遍历，默认最大深度 64、结构节点 200,000，超过立即抛解析错误；JSONL 给每行建立独立根路径。

8. XML 如何防止 XXE？XPath 信息怎样进入引用？

   **回答（已实现）：** 使用 `defusedxml.ElementTree`，危险实体或无效 XML 会被拒绝；同样限制深度和节点数。每个元素生成带兄弟序号的 XPath，写入 ParsedUnit metadata 并随 Chunk 入库；当前 API Citation 模型没有单独 xpath 字段，定位信息主要存在 Chunk metadata 中。

9. 压缩包格式的 DOCX/XLSX/PPTX 如何防止 Zip Bomb 和路径穿越？

   **回答（已实现）：** 上传时验证 ZIP 签名和对应的 `word/`、`xl/`、`ppt/` 目录；逐成员拒绝绝对路径和 `..`、加密成员，限制成员数 10,000 和总解压声明大小 250 MB。还需注意声明大小并非所有压缩攻击的绝对防线，生产可在沙箱中限制 CPU、内存和磁盘。

10. 图片为什么同时执行 OCR、视觉描述和原始图片 Embedding？三者分别解决什么问题？

    **回答（已实现）：** OCR 提取可引用文字，视觉模型补图表关系和版面语义，原图 VL Embedding 支持跨模态检索。三者互补：只 OCR 会丢图形关系，只描述会丢精确文字，只图向量又不适合直接给生成模型做文本引用。

11. 文本、表格、图片为什么使用独立 Chroma 集合？

    **回答（已实现）：** 三种模态的编码方式和分数分布不同，独立集合便于使用 bge-m3 与 VL Embedding、独立统计和调权，再在排名层融合。集合分别是 `knowledge_text_v2`、`knowledge_table_v2`、`knowledge_image_v2`，并兼容读取 legacy 集合。

12. 跨模态文本查图时，查询向量和图片向量为什么能比较？

    **回答（已实现并预检）：** Qwen3-VL-Embedding 把文本和图片映射到同一个 1024 维语义空间；查询时除普通文本向量外，还生成 VL 文本查询向量，图片集合使用该向量搜索。真实预检验证了文本/图片维度一致，但没有完成大规模跨模态检索质量基准。

13. 视觉模型不可用时，系统如何降级并向用户暴露降级信息？

    **回答（已实现）：** `_vision_description` 捕获异常，返回空描述和错误类型，OCR 内容仍继续；入库结果的 `vision_fallbacks/partial_failures` 暴露降级原因，trace 和日志不包含密钥。视觉被禁用或未配置也会走 OCR，但该状态不计为部分失败。

14. 一张图片失败是否应该导致整份文档失败？为什么？

    **回答（当前策略）：** 视觉描述或个别 Office 图片解码失败不应阻断其他可用内容，因此当前降级或跳过；但原始独立图片完全无法解析、VL Embedding 写入失败、主文件结构损坏会使事务失败。生产版还应配置允许的图片失败比例和质量告警，避免“成功”却丢失大部分内容。

## 七、知识图谱与来源治理

1. Entity、Chunk、`MENTIONED_IN` 和业务 `RELATION` 的 Schema 是什么？

   **回答（已实现）：** Entity 有 key、name、type、description 和时间；Chunk 有 chunk_id、doc_id、content、source、file/page/sheet、modality、asset_path 和 version；Entity 通过 MENTIONED_IN 指向 Chunk；Entity 间 RELATION 保存 predicate、confidence、source_chunk_id、version。Entity key 与 Chunk ID 都有唯一约束。

2. 实体规范化如何处理别名、同名实体和中英文名称？

   **回答（当前缺口）：** 当前只用 `lower(trim(name))` 合并大小写和前后空格，抽取内用“名称+类型”去重；没有真正的别名词典、实体链接或同名消歧，所以“微软/Microsoft”或同名人物可能分裂或误合并。生产版需要租户领域词典、别名边和人工审核。

3. LLM 结构化抽取不符合 Pydantic Schema 时如何重试？

   **回答（已实现）：** 从响应中截取 JSON 对象，用 ExtractionResult/Pydantic 校验实体、关系和置信度；失败会把简短错误反馈给模型重新输出，按 `llm_max_retries=2` 最多额外重试两次。最终仍失败就抛错，使入库回滚，不把错误字符串当知识。

4. 每条实体和关系为什么必须保存 `source_chunk_id`？

   **回答（已实现）：** 它让事实能回到原文、支持引用、版本更新和精确删除。没有来源时，删除一个文档无法判断某条关系是否仍被其他文档支持，也无法审计图谱错误来自哪个 Chunk。

5. 为什么把业务关系存成统一的 `RELATION {predicate, confidence}`，而不是动态关系类型？

   **回答（已实现）：** 动态关系类型需要把模型文本拼进 Cypher，容易注入、类型爆炸且难做统一查询。通用 RELATION 固定 Schema，predicate 作为数据参数，既保留语义又便于索引、删除和迁移。

6. 删除一个 Chunk 时，哪些图节点和关系可以删，哪些必须保留？

   **回答（已实现）：** 删除 source_chunk_id 对应的业务 RELATION、Chunk 节点和随 Chunk 消失的 MENTIONED_IN；Entity 本身只有在既无 MENTIONED_IN 又无任何 RELATION 时才删除。其他文档仍提及或参与关系的 Entity 必须保留。

7. “孤立实体”如何判断？多个文档共同引用同一实体时如何处理？

   **回答（已实现）：** 清理查询要求 Entity 不再指向任何 Chunk，且不再参与任何 RELATION。Entity 使用唯一 key 合并，所以多个文档会产生多条 MENTIONED_IN；删除其中一篇不会删除仍有其他来源的实体。

8. 图谱中的错误事实如何溯源、纠正和重新抽取？

   **回答（部分实现）：** 可以用 source_chunk_id 找到原始文档和版本，修改文档后 CDC 会删除旧来源关系并重新抽取，或用 rebuild 重建整篇。当前没有业务人员图谱审核 UI 和“人工纠正优先于模型重建”的覆盖层，这是知识治理缺口。

9. 图检索结果如何评分并参与 RRF？

   **回答（已实现）：** 初始启发分根据匹配实体数和跳数计算，再混入 30% 的查询词与 Chunk/实体/谓词词法重叠；按该分数排序后进入 RRF。Hybrid 最终只使用图候选的排名，不直接与向量原始相似度相加。

10. Neo4j 不可用时，问答是否可以退化为纯向量模式？

    **回答（部分实现）：** Hybrid 的图分支异常会记录并使用向量分支继续，运行时具备单路降级；但 `/health/ready` 当前要求 Neo4j 健康，否则整体返回 503。生产上可区分 full-ready 与 degraded-ready，并配合告警，而不是长期静默降级。

## 八、CDC、幂等与一致性

1. 稳定 chunk_id 由哪些字段生成？为什么需要“重复序号”？

   **回答（已实现）：** 使用 doc_id、unit_id、规范化内容 SHA-256 和同一 unit 内相同内容的 occurrence，最终再哈希成 32 位 ID。重复序号用于区分同一来源单元里内容完全相同的多个片段，否则它们会发生主键冲突。

2. 内容哈希与 chunk_id 的职责有什么区别？

   **回答：** content_hash 只描述规范化内容，可用于判断内容相同；chunk_id 还包含文档和来源位置语义，用作跨存储主键和 Diff。相同文字出现在两篇文档或不同章节时内容哈希可相同，但 chunk_id 应不同。

3. 更新后如何计算 added、changed、deleted、unchanged？

   **回答（已实现）：** 当前用 old_ids 与 new_ids 做集合差：new-old 是 added，old-new 是 removed，交集是 unchanged。由于 ID 包含内容哈希，内容改变会形成“一条 removed + 一条 added”，没有单独 changed 集合；对外可以概念上称变化块，但代码计数是新增与删除。

4. 为什么只对新增和变化 Chunk 重新 Embedding？

   **回答（已实现）：** Embedding 和抽取有外部 API 成本，未变化 Chunk 的向量与图来源仍有效。只处理 added 可以降低调用数并保持来源稳定；项目具备这一机制，但 AKH-CDC-300 的 token 降幅和加速倍数尚未正式跑完，不能引用 80%/5 倍目标为结果。

5. 文档局部修改导致后续分块边界整体漂移时，如何提高未变化 Chunk 保留率？

   **回答（当前方案与边界）：** 先按页、标题、工作表、JSONPath 等稳定 unit 切分，再在 unit 内滑窗，能把漂移限制在局部；ID不使用全局 chunk_index。但一个长 unit 前部插入文本仍可能使后续 token 窗整体漂移，生产可加入内容定义分块、句子锚点或相似块匹配。

6. Kafka 的 at-least-once 语义下如何保证业务幂等？

   **回答（已实现）：** event_id 是 SQLite 主键，claim_event 原子地阻止 COMMITTED/APPLYING 重入；Chroma/Neo4j 写操作采用 upsert/delete，成功后才提交 offset。消息重复投递会被识别为 duplicate，不重复提交文档版本。

7. 消费成功但提交 offset 前进程崩溃，重放后会怎样？

   **回答（已实现）：** 业务事件在 SQLite 已是 COMMITTED，Kafka 重放相同 event_id 时 update 图直接产生 duplicate result，然后消费者把该消息 offset 提交。这样用业务幂等承接 Kafka 至少一次语义。

8. Chroma 写成功、Neo4j 写失败、SQLite 尚未提交时如何补偿？

   **回答（部分实现）：** 入库异常会删除本次 added_ids 在 Chroma 与 Neo4j 的记录，并把文档标记 FAILED；旧 catalog Chunk 在 commit 前仍保留。补偿本身也可能失败，所以还有跨存储检查和 repair/rebuild；这不是原子事务，生产版需要持久化每一步操作日志。

9. 为什么采用状态机和修复命令，而不是声称实现跨存储强事务？

   **回答：** SQLite、Chroma 和 Neo4j 没有共同事务协调器，强行声称 ACID 不真实。状态机、幂等写、校验和补偿属于 Saga/最终一致性思路，能明确失败位置并重复执行；同时要承认存在短暂不一致窗口和修复成本。

10. 全量重建的用途是什么？如何与增量结果做一致性对比？

    **回答（已实现命令，性能未完整实测）：** rebuild 对指定 doc_id 强制删除并重新解析、向量化和建图，是故障恢复基线。正确性评测应对同一最终文件分别运行事件增量和全量重建，比较 catalog、向量 Chunk ID、图 Chunk/关系来源；当前修复命令存在，但 CDC-300 完整量化报告未完成。

11. 如何量化增量更新收益：Embedding token、更新时间还是未变化 Chunk 保留率？

    **回答：** 三者都要报告：未变化保留率反映算法稳定性，Embedding token 降幅反映成本，端到端中位加速反映性能；同时要保证最终状态与全量重建一致和事件幂等 100%。只报速度而不报一致性没有意义。

12. 当前项目是否已经实测“更新效率提升 95%”？如果没有，应如何回答？

    **回答（实际边界）：** 没有。仓库准备了 AKH-CDC-300 和相关指标代码，但当前正式报告没有完成这组全量对照，所以我只讲“实现了按稳定 Chunk ID 的增量更新机制”，不写提升 95%。

## 九、工程质量、安全与可观测性

1. `/health/live` 与 `/health/ready` 有什么区别？

   **回答（已实现）：** live 只表示 FastAPI 进程能响应；ready 并发检查 Chroma、Neo4j、Kafka、目录库和模型配置，任一必需项失败返回 503。这样编排平台不会因为进程活着就把依赖不完整的实例接入流量。

2. 外部模型、Chroma、Neo4j、Kafka 分别不可用时，ready 应返回什么？

   **回答（已实现）：** checks 中对应项为 false，并返回 503 和 `not_ready`。它只检查模型是否配置，不在每次健康检查中调用付费模型；当前 catalog 固定记 true，生产版还应执行轻量 SQLite 读写或连接检查，并区分问答降级可用与入库不可用。

3. 重试哪些错误，为什么 4xx 通常不应盲目重试？

   **回答（部分实现）：** Reranker 只重试 408、429、5xx 和传输错误；结构化 LLM 输出会重试修复。LangGraph 通用 `_retry_stage` 当前对所有异常重试两次，这比生产策略宽，后续应只对白名单瞬时错误重试；认证失败、参数错误等 4xx 重试只会放大流量。

4. 如何避免日志、异常、评测缓存和 Git 中泄露 API Key？

   **回答（已实现基础）：** 密钥只从 `.env`/环境变量读取，`.env` 被 Git 和 Docker build context 排除；对外错误返回通用诊断提示，Reranker 统计不记录 header 或正文，评测报告只记录模型和用量。生产版应改用 Secret Manager、日志脱敏和定期密钥轮换。

5. 上传接口如何校验扩展名、MIME、文件签名和文件大小？

   **回答（已实现）：** 先用安全 basename 拒绝路径，扩展名必须在白名单，content-type 必须匹配；流式按 1 MB 写入并限制默认 50 MB，拒绝空文件；PDF/PNG/JPEG 验 magic bytes，Office 验 ZIP 和内部目录，文本类拒绝头部 NUL 字节。

6. 如何防止目录穿越、恶意 XML、Zip Bomb、超大工作表和深层 JSON？

   **回答（已实现）：** 上传路径固定为 `uploads/{doc_id}/{safe_name}`；Office 成员拒绝绝对路径和 `..` 并限制数量/总大小；XML 用 defusedxml；表格默认最多 100,000 行；JSON/XML 深度 64、节点 200,000。资源级 CPU/内存沙箱仍属于生产补充。

7. Fake Chat、Fake Embedding、Fake Vision 和 Fake Reranker 各自验证什么？

   **回答（已实现）：** Fake Chat 验证结构化抽取/计划/回答契约，Fake Embedding 验证向量写查和调用复用，Fake Vision/VL 验证 OCR 降级、原图资产和跨模态集合，Fake Reranker 验证排序、重试、异常索引与 fallback。它们保证代码确定性，不证明真实模型质量。

8. 当前 126 项自动测试和 87.94% 覆盖率能证明什么，又不能证明什么？

   **回答（实测）：** 能证明核心分支、格式、安全、幂等、检索融合和指标公式有回归保护；Docker 还做了真实后端读写与 11 格式 Fake E2E。覆盖率不能证明语义答案正确、真实模型稳定、千级规模性能或没有并发故障，因此仍需真实预检、基准和压测。

9. 为什么 CI 不依赖真实付费 API？真实 API 预检应该放在哪一层？

   **回答：** PR CI 需要可重复、快速、无密钥和无费用，外部 API 波动不应阻塞代码回归。真实预检应放在受控的手动/定时环境，使用最小样本验证模型权限、响应 Schema、向量维度和分数方向；项目已经执行过视觉/VL 预检，并把 live E2E 默认 deselect。

10. 如何观测各 Agent 的耗时、重试、fallback、token 和错误率？

    **回答（部分实现）：** API 返回 retrieval/generation/total 时间和高层 trace；模型 wrapper、Embedding 与 Reranker记录调用、token、错误、重试和 p50/p95，admin stats 汇总目录、向量和图谱数据。当前缺少 Prometheus/OpenTelemetry、跨服务 trace_id 看板和告警规则，仍是本地观测能力。

11. 如何做模型调用限流、超时、熔断和降级？

    **回答（部分实现/生产方案）：** 当前有超时、有限重试、抽取并发信号量和 Rerank fallback，但没有集中式限流器与熔断器。生产会按供应商建立独立并发池和 token bucket，达到错误率阈值熔断；问答降级为少候选/Vector-only，视觉降级 OCR，入库任务排队而不是同步重试风暴。

12. 如果 Chroma 的 v1 旧集合与 v2 多模态集合共存，如何保证迁移幂等？

    **回答（已实现）：** `akh-admin migrate-multimodal` 支持 dry-run、doc_id 和断点式逐文档迁移，先检查 v2 已存在 ID，只补 missing；查询时 v2 已有的 Chunk 会从 legacy 候选中过滤，避免重复 RRF 加分。验证完成前不删除 legacy 集合。

## 十、系统设计追问

1. 如果系统需要支持 10 万日活、每人每天 5 次提问、p95 小于 2 秒，整体架构如何改造？

   **回答（生产方案）：** 日请求约 50 万，平均约 5.8 QPS，但要按峰值几十到上百 QPS 设计。入口用网关做 SSO、租户、限流；无状态 Query 服务水平扩容；Embedding/Vector/Graph 并行并加 Redis；生成走独立模型网关和流式响应；入库/OCR/抽取/CDC 放异步队列和 Worker；原文进对象存储。当前单机 Compose 没有实测该规模。

2. 2 秒 SLA 是否包含 LLM 生成时间？如果包含，如何实现流式首 token 与完整响应分离？

   **回答（生产方案）：** 必须先定义清楚。外部大模型完整生成 p95 通常难保证 2 秒，我会把 2 秒定义为检索完成或首 token SLA，完整答案另报；检索预算约 300–500 ms，超时降级图扩展/二次检索，HTTP 使用 SSE 流式输出并记录 TTFT 与完成时间。

3. 多租户场景下，逻辑隔离与物理隔离分别如何设计？

   **回答（生产方案）：** 普通租户可共享集群但所有记录强制 tenant_id、服务端注入过滤和独立密钥；高合规租户使用独立 bucket、向量集合/数据库、Neo4j database、关系库 schema、Kafka topic/ACL，甚至独立集群。当前项目没有认证和 tenant_id，不能声称已实现隔离。

4. 租户 ID 应在哪些层强制注入，如何避免模型生成过滤条件？

   **回答（生产方案）：** 网关从签名身份解析租户，服务端上下文向对象存储路径、目录 SQL、向量 where、Cypher 参数、缓存 key 和审计日志强制注入；客户端和 LLM 都不能自由提供 tenant_id。所有查询模板在数据访问层再做一次强制校验。

5. 早高峰流量突增 3 倍时，如何通过队列、限流、缓存、背压和降级避免雪崩？

   **回答（生产方案）：** 入口按租户限流，异步任务队列削峰，在线查询按队列和 p95 自动扩容；依赖各自有 bulkhead、超时和熔断；缓存查询向量和热点结果。过载时减小候选数、关闭图/二次检索或返回稍后重试，重试只对幂等瞬时错误并带指数退避和 jitter。

6. 在线问答与离线入库为什么应该使用不同资源池？

   **回答（生产方案）：** OCR、解析和图谱抽取是长耗时、CPU/模型密集任务，如果与在线问答共享 Worker，会造成 head-of-line blocking。应拆队列、Deployment、并发配额和优先级，保证问答 SLA，同时让大文件入库按吞吐处理。

7. 上传 1000 页 PDF 时，如何拆任务、报告进度、局部重试和断点续传？

   **回答（生产方案）：** API 只创建 upload/job，原件分片上传对象存储；调度器按页或页段产生 parse/OCR 任务，结果写 staging manifest，后续批量分块、Embedding 和抽取。进度按总页数与阶段汇总，失败只重试对应页段，所有页验证后切换 active version。当前同步接口最多 500 页，不具备这套生产任务 API。

8. 超长文档如何使用章节级索引、父子 Chunk 和文档内二次检索提高召回？

   **回答（已实现基础+生产方案）：** 当前已保留页/章节/工作表 unit，建立 350/50 子块与 900/100 父块映射，并在精排时补父块和相邻窗口；候选文档内还会复用查询向量做二次检索。当前父块保存在 SQLite 元数据中、只用于上下文扩展，还不是独立的章节向量索引；生产可进一步建立文档摘要—章节—细粒度 Chunk 三层索引。

9. 系统成本最高的是生成、Embedding、Rerank、OCR 还是图谱抽取？如何用实测数据判断？

   **回答：** 不能凭经验下结论。通常生成和逐 Chunk 图谱抽取 token 最贵，首次 OCR/视觉也可能高；应按 request/job 记录各模型输入输出 token、调用数、单价、CPU 时间和存储成本，计算单问、单文档及每租户成本。当前 stats 已记录部分用量，但没有完整生产账单归因。

10. 如果要求推理成本降低 30%，你会优先优化哪些调用？

    **回答（生产方案）：** 先用账单定位，再优先做查询计划/Embedding缓存、Rerank 压缩上下文、简单题小模型或直接抽取、时间/数值题确定性工具、限制输出长度和仅对新增 Chunk 抽取。每项都在固定集上守住 Recall、EM、引用和拒答，不会只换便宜模型就宣布成功。

11. 如何设计问答缓存，避免权限变化或知识更新后返回过期答案？

    **回答（生产方案）：** 缓存 key 至少包含 tenant、user/role 权限摘要、规范化问题、检索策略、模型版本和知识库 active_version；文档更新或 ACL 变化按依赖 doc_id/版本失效。高风险答案可只缓存 QueryPlan、Embedding 和候选，不缓存最终文本。

12. 如果需要灰度升级 Embedding 模型，如何双写、回填和无损切换索引？

    **回答（生产方案）：** 新建带模型版本和维度的新集合，新写双写，后台按文档断点回填；用固定集和线上 shadow 比较 Recall/延迟/成本，校验覆盖率后把读流量逐步切到新集合。保留旧集合至观察期结束，可随时切回，不能原地混放不同维度向量。

13. 怎样定义 SLO，并监控 p50/p95、成功率、拒答率、引用有效率和单位问题成本？

    **回答（生产方案）：** 先按用户旅程定义可用性、TTFT、完整延迟、正确引用率和数据新鲜度 SLO，再从日志/trace 计算 p50/p95、错误预算和每问成本；按租户、题型、策略和模型分桶。拒答率不能单独追低，要与误答率和无答案集 Rejection F1 一起看。

## 十一、生产级落地与线上运维

> 这一部分主要考察“当前 MVP 如果要真正进入企业生产环境，你会怎么继续设计”。回答时必须区分**仓库已经实现的能力**和**生产化改造方案**。

### 11.1 容量规划与性能

1. 上线前需要收集哪些容量参数：文档数、Chunk 数、日增量、QPS、并发数、平均输入输出 token 还是文件大小？

   **回答（生产方案）：** 都需要，并且要按租户和峰值分布采集。我会统计文档/页/Chunk 总量与日增、文件类型和大小、查询 QPS/并发、Top-K、模型 token、索引增长、更新频率和冷热比例，再用压测而不是平均值做容量基线；当前仓库尚无生产容量数据。

2. 如何根据 DAU、提问频率和峰值系数估算平均 QPS、峰值 QPS 与所需实例数？

   **回答（生产方案）：** 10 万 DAU×5 问约 50 万次/日，平均约 5.8 QPS；再按业务小时占比、早高峰和突发系数估到几十或上百 QPS。单实例容量要通过目标延迟下的压测得到，实例数按 `峰值QPS/单实例安全QPS` 再加故障冗余，而不是只按 CPU 猜。

3. 这个系统的 p95 延迟预算如何拆分给网关、QueryPlan、Embedding、检索、Rerank、LLM 生成和引用校验？

   **回答（生产方案）：** 先把端到端预算分成不可控模型时间和可控检索时间，例如 2 秒 TTFT 中网关 50 ms、计划/缓存 150 ms、Embedding 100 ms、并行检索 250 ms、Rerank 250 ms、组装校验 50 ms，其余给模型首 token。实际比例必须用 trace 校准，超预算阶段有明确降级。

4. 如果 p95 要求 2 秒，但外部 LLM 本身需要 5 秒，产品和技术契约应该如何调整？

   **回答（生产方案）：** 不能靠架构掩盖物理不可能。我会把 2 秒改成检索完成或首 token SLO，完整答案单独定义；如果完整答案必须 2 秒，只能限制输出、使用更快/本地小模型、预生成或对简单题走模板，并让产品接受质量取舍。

5. 如何区分首 token 延迟、完整回答延迟和纯检索延迟？对用户体验分别有什么影响？

   **回答（生产方案）：** TTFT 决定用户多久看到响应开始，完整延迟决定任务真正结束，检索延迟反映 RAG 后端效率。三者应分别埋点；流式能改善 TTFT 体验，但不能把 10 秒完整生成包装成 p95 2 秒。

6. Chroma 和 Neo4j 的容量瓶颈分别可能出现在 CPU、内存、磁盘、索引还是网络？

   **回答（生产方案）：** Chroma 主要受向量索引内存、磁盘 IO、维度、过滤和并发查询影响；Neo4j 主要受热点图是否进 page cache、遍历分支因子、查询计划和磁盘影响，容器网络也会增加尾延迟。当前单节点 Compose 只用于 MVP，必须用真实数据规模分别压测。

7. 文档达到百万 Chunk 后，当前 Chroma 部署是否还能满足要求？什么时候需要分片或更换向量数据库？

   **回答（实际边界）：** 当前没有百万 Chunk 实测，不能保证。若索引无法在目标资源下满足 p95、写入/备份/多租户能力不足，或需要水平分片和高可用，就应评估 Milvus、Qdrant、Weaviate、pgvector 或托管服务；迁移依据是基准与运维需求，不是名称偏好。

8. 图谱达到千万级关系后，1–3 跳查询如何避免节点爆炸和慢查询？

   **回答（生产方案）：** 入口实体必须有唯一索引，查询按租户/文档/关系类型和时间过滤，限制 frontier、每跳 fan-out、总结果与超时；高频路径可预计算或缓存。上线前用 EXPLAIN/PROFILE 找笛卡尔积和全图扫描，并对超节点单独治理。

9. 在线问答、文档解析、OCR、Embedding 和图谱抽取为什么应该拆成不同队列与资源池？

   **回答（生产方案）：** 它们的 SLA、资源类型和耗时分布不同，大 OCR 任务不能挤占在线查询线程。拆池后可分别扩容、限流和设优先级，故障也不会级联；当前 Compose 中都在一个 API 进程，是 MVP 的生产缺口。

10. 如何做压力测试、稳定性测试和长时间 Soak Test？验收指标是什么？

    **回答（生产方案）：** 用脱敏真实大小分布构造读写混合流量，逐级升 QPS 找饱和点，再在目标负载持续 24–72 小时观察内存泄漏、连接池、Kafka lag 和索引增长。验收看错误率、p95/p99、TTFT、资源水位、数据一致性、积压恢复和单位成本；当前未完成该类规模压测。

11. 如何避免单个 1000 页 PDF 或超大批量上传耗尽全部 Worker？

    **回答（生产方案）：** 上传只创建任务，按租户限制文件和并发，页段任务进入低优先级队列；Worker 设置 CPU/内存/执行时间和每任务页数上限，调度器使用公平队列。当前已有限制 50 MB、500 页和批量并发 2，但还不是分布式隔离。

12. 如果 Reranker 成为延迟瓶颈，会减少候选数、换小模型、做缓存，还是直接降级？如何选择？

    **回答（生产方案）：** 先看候选数—Recall—延迟曲线；优先缓存相同 query/候选签名并按题型减少 candidate_k，其次评估小模型或本地部署。超时可回退 RRF，当前已有该降级；长期关闭前必须验证 Answer/Citation 指标不会明显下降。

### 11.2 高可用、故障恢复与灾备

1. FastAPI、Kafka、Chroma、Neo4j 和 SQLite 中，哪些组件当前存在单点故障？

   **回答（实际边界）：** 当前 Compose 中 FastAPI、Kafka、Chroma、Neo4j 都是单实例，SQLite 目录和 Checkpoint 还是本地文件，因此全部存在单点。Docker healthcheck 不等于高可用；生产要无状态 API 多副本、Kafka/数据库集群和共享高可用元数据存储。

2. SQLite Checkpointer 在多实例部署下会遇到什么问题？生产环境应该如何替换？

   **回答（生产方案）：** 每个实例看到自己的本地文件，同一 thread 可能落到不同实例，锁竞争、故障转移和共享状态都不可控。生产应换成 LangGraph 支持的 PostgreSQL 等共享 Checkpointer，配合任务租约和唯一执行约束。

3. Kafka 如何设置副本数、ISR、ACK、消费者组和重试队列，避免事件丢失？

   **回答（生产方案）：** 至少 3 broker、topic replication factor 3、min.insync.replicas 2、producer `acks=all` 并开启幂等；消费者手动提交 offset，失败进入带重试次数的 retry topic，最终 DLQ。当前单节点 KRaft、副本 1 只适合本地开发。

4. 消费失败三次后是进入死信队列、暂停分区，还是跳过事件？如何告警和人工修复？

   **回答（当前+生产方案）：** 当前事件到 3 次后保持 FAILED，offset 不提交，会阻塞该分区，没有完整 DLQ。生产应把不可恢复事件连同错误、文档版本和 trace 写 DLQ，再提交原 offset，触发告警和工单；管理员修复后以新 event_id 重放，并保留审计。

5. Neo4j 或向量数据库短暂宕机时，问答与入库分别应该快速失败、排队等待还是降级？

   **回答（生产方案）：** 问答可在单依赖故障时快速降级为可用检索分支并标记 degraded，双路失败快速返回；入库不能半成功对外可见，应保留 staging 任务并延迟重试。当前 Hybrid 支持单路 fallback，但入库主要靠同步重试和 FAILED/repair。

6. 如何定义 RPO 和 RTO？文档原文件、目录库、向量索引和知识图谱分别如何备份？

   **回答（生产方案）：** 先由业务确定可丢数据时间 RPO 和恢复时间 RTO。原件进版本化对象存储；关系目录做持续 WAL/快照；Neo4j 按版本备份；向量索引可备份也可从原件重建；Kafka 保留足够事件窗口。当前项目没有正式 RPO/RTO 和自动备份演练。

7. Chroma 与 Neo4j 从不同时间点备份恢复后数据不一致，如何发现并修复？

   **回答（现有基础+生产方案）：** 用 active document version/manifest 中的 Chunk ID 作为期望集合，扫描两库差异并按文档 rebuild；当前 repair 已用 SQLite Chunk 集合做这个检查。生产应给快照打同一逻辑 epoch，恢复后先离线校验再接流量。

8. 如何通过原始文档和 SQLite 目录重建向量索引与知识图谱？重建期间是否允许查询？

   **回答（现有基础+生产方案）：** 当前 `akh-admin rebuild <doc_id>` 可强制重建单文档。生产全量重建应写新索引/图版本，旧版本继续只读服务，完成校验后原子切别名；不能在用户正在读的唯一集合上边删边建。

9. 外部模型 API 大面积超时或限流时，如何使用超时、重试、熔断、隔离舱和降级避免级联故障？

   **回答（生产方案）：** 每类模型独立连接池和并发上限，短超时、有限指数退避和随机抖动；错误率超阈值熔断，半开探测恢复。查询降级为缓存/小模型/RRF，视觉降级 OCR，离线任务排队；当前有超时、重试和部分 fallback，但无集中熔断。

10. 如果硅基流动或反代服务长期不可用，是否需要备用模型供应商？怎样保证输出契约一致？

    **回答（生产方案）：** 高可用场景需要主备，但不是简单换 Base URL。用统一 adapter、Pydantic Schema、能力注册和固定回归集验证 Chat/Embedding/VL/Rerank 的维度、分数方向和结构化输出；Embedding 供应商切换通常需要新索引，不能直接混用。

11. 如何设计跨机房或跨可用区部署？Kafka、Neo4j 和对象存储各自怎样容灾？

    **回答（生产方案）：** 无状态 API 跨 AZ 部署；Kafka 副本跨 AZ 并设置 rack awareness；Neo4j 使用支持集群的版本/托管方案；对象存储跨区复制；控制面数据库同步复制。跨地域要权衡延迟、一致性和数据合规，当前 Community 单节点不具备这些能力。

12. 如何定期演练数据恢复，而不是只确认“存在备份文件”？

    **回答（生产方案）：** 定期在隔离环境从备份恢复，运行 Chunk/关系/引用一致性检查和抽样问答，记录实际 RPO/RTO；再做单组件宕机和整站恢复演练。备份未经过恢复验证就不能算可用。

### 11.3 多租户、身份认证与权限控制

1. 企业员工如何接入：OIDC、OAuth2、LDAP、企业微信还是内部 SSO？

   **回答（生产方案）：** 优先接企业现有 IdP，用 OIDC/OAuth2 获取签名身份，必要时由统一身份平台桥接 LDAP/企业微信。应用不自己保存员工密码；当前项目无认证，只能作为内网演示 MVP。

2. 用户、角色、部门、租户、文档和 Chunk 之间的权限模型如何设计？

   **回答（生产方案）：** 采用租户边界上的 RBAC + 文档级 ACL/ABAC：角色给基础权限，部门、密级、项目和文档 owner 决定具体可见范围；Chunk 继承文档 ACL。权限规则存权威关系库，索引中只保存用于预过滤的不可伪造标签。

3. ACL 应该在检索前过滤、检索后过滤，还是两层都做？为什么只做检索后过滤可能泄露信息？

   **回答（生产方案）：** 必须检索前强过滤，检索后再防御性校验。只做后过滤会让未授权文档参与排名、日志、缓存甚至 Reranker/LLM 请求，产生侧信道和内容外发风险。

4. Chroma、Neo4j、缓存和日志中如何强制携带 tenant_id 与权限条件？

   **回答（生产方案）：** 数据访问层从认证上下文强制注入 tenant/ACL，Chroma where、Cypher 参数、缓存 key 和日志字段都不能由用户覆盖；写入时也验证 doc 归属。当前 Schema 没有 tenant_id，需要作为生产改造的跨层字段加入。

5. 为什么不能让 LLM 自己决定用户是否有权访问某篇文档？

   **回答：** LLM 输出是概率性的，也容易受 Prompt Injection 影响，不能作为安全控制点。授权必须由服务端基于签名身份和确定性策略执行，模型只接触已经过滤的证据。

6. 如何防止用户通过提示词诱导模型引用其他部门或其他租户的数据？

   **回答（生产方案）：** 在检索前根本不让未授权数据进入候选，工具参数由服务端注入租户条件，最终 citation 再做 ACL 校验；缓存按权限摘要隔离。Prompt 只能是辅助约束，不能替代数据层隔离。

7. 多租户物理隔离时，是每租户独立数据库、独立集合、独立 Schema 还是独立集群？如何权衡成本？

   **回答（生产方案）：** 按合规等级分层：中小租户共享集群+逻辑隔离，高敏租户独立数据库/集合和密钥，极高要求租户独立集群与网络。依据监管、数据规模、性能噪声和成本选择，不会所有租户一刀切。

8. 文档权限发生变化后，缓存、索引和正在运行的会话如何及时失效？

   **回答（生产方案）：** 权限变更产生事件，提升 ACL version，缓存 key 包含该版本并主动删除相关 doc 依赖；检索和回答返回前再次用最新权限校验。长会话不能沿用旧上下文，下一轮必须重新授权。

9. 一个用户对答案有访问权，但对某条原文没有访问权时，是否可以返回答案？

   **回答：** 原则上不可以通过受限原文派生答案，否则仍是信息泄露。除非企业有经过审批的脱敏派生数据和独立授权策略，否则答案可见性不能高于其证据可见性。

10. 管理员上传、删除、重建和迁移操作如何审批和审计？

    **回答（生产方案）：** 高风险操作走 RBAC、MFA 和可选双人审批；审计记录 actor、tenant、doc、旧新版本、原因、时间、结果和 trace_id，日志写不可篡改存储。当前 admin API 没有认证审批，不是生产接口。

11. API Key、模型密钥和数据库凭据如何通过 Secret Manager 托管和轮换？

    **回答（生产方案）：** 使用云 Secret Manager/Vault/Kubernetes External Secrets 按服务身份动态注入，不写镜像和仓库；密钥最小权限、短周期轮换、双 key 过渡并审计访问。当前 `.env` 只是本地开发方式。

12. 如何对下载、检索、问答、删除等行为记录不可抵赖的审计日志？

    **回答（生产方案）：** 统一审计事件包含认证主体、租户、资源、动作、策略结果、时间和 trace_id，敏感正文只存哈希/引用；日志追加写入受保护的集中存储并设置保留策略。普通应用日志不能替代审计日志。

### 11.4 数据安全、隐私与合规

1. 企业文档中出现身份证号、手机号、合同金额和商业机密时，入库前是否需要识别与脱敏？

   **回答（生产方案）：** 需要按数据分类策略决定：可做 DLP 扫描、标记密级、阻断或生成脱敏副本；原件与索引采用不同权限。当前项目没有 PII 检测，不能直接用于高敏文档生产入库。

2. 将企业文档内容发送给外部 LLM、Embedding 或 Rerank 服务前，需要满足哪些数据合规条件？

   **回答（生产方案）：** 确认数据分类允许外发、供应商合同与地域、是否训练/留存、传输加密、删除和审计能力，并获得企业安全/法务批准。高敏数据应走本地或专有部署，当前真实 API 仅用于测试数据预检。

3. 如何实现敏感级别不同的文档走不同模型：公网 API、专有云或本地模型？

   **回答（生产方案）：** 入库时给文档打密级，模型网关根据 tenant+classification 路由到允许的 provider，并在调用前再次执行 DLP；索引和缓存也按级别隔离。策略由服务端配置，用户和 LLM不能绕过。

4. 数据在传输中和静态存储时如何加密？密钥由谁管理？

   **回答（生产方案）：** 外部和服务间使用 TLS/mTLS；对象存储、数据库磁盘、备份和日志使用 KMS 管理的静态加密，高敏租户可自带密钥。密钥由安全平台管理，应用只拿临时权限；当前本地 Compose 使用明文开发凭据，不符合生产要求。

5. 日志、trace、异常堆栈和评测缓存中如何避免保存问题正文和敏感上下文？

   **回答（现有基础+生产方案）：** 当前 trace 只记录阶段，不返回思维链，外部错误也不回显正文或密钥。生产会默认只记录 request/doc 哈希、长度和分类，对正文采样需审批并脱敏；评测缓存放受控存储并设 TTL，而不是提交仓库。

6. 用户要求删除文档时，如何证明原文件、资产、Chunk、向量、图关系、缓存和备份都按策略处理？

   **回答（当前+生产方案）：** 当前 delete 会清理受管上传、资产、SQLite、所有向量集合和 Neo4j 来源。生产还要生成删除任务清单和完成证明，清理缓存/副本；备份通常按保留周期和 tombstone 处理，并在恢复时重新应用删除记录，而不能承诺立即物理擦除所有备份。

7. 如何设置数据保留周期、Legal Hold 和自动过期策略？

   **回答（生产方案）：** 文档记录保存 retention_policy、expires_at 和 legal_hold；定时任务只删除到期且无 hold 的数据，并走同一审计删除链。当前 catalog 没有这些字段。

8. 第三方模型供应商是否会保留请求数据？上线前如何完成供应商风险评估？

   **回答（生产方案）：** 查合同和服务条款而不是假设，确认留存、训练、分包商、地域、加密、事故通知和删除机制；安全/法务完成评审并定期复核。若不能满足，使用专有或本地部署。

9. Prompt Injection 藏在 PDF 或网页正文中时，如何防止文档内容控制系统指令或调用工具？

   **回答（生产方案）：** 把文档标记为不可信数据，用结构化边界传入，系统 Prompt 明确不可执行文档指令；工具使用白名单和参数校验，授权不交给模型，高风险操作需确认。当前系统没有可写外部工具，但仍需要专门的间接 Prompt Injection 测试。

10. 如何防止模型在答案中大段泄露原文，而不仅仅是返回短引用？

    **回答（生产方案）：** 在生成策略限制引用长度和逐字复现比例，输出后做相似片段/DLP 检测，高密级文档只允许摘要；同时按用户权限控制。当前 citation quote 截断 300 字符，但答案正文还没有完整的防大段复现检查。

11. 上传恶意文件时，除了格式校验，是否需要病毒扫描、沙箱解析和内容安全检测？

    **回答（生产方案）：** 需要。当前有路径、签名、压缩包、XXE和结构限制，但生产应先用杀毒/内容拆解扫描，解析 Worker 无特权、只读、限制出网和资源，异常文件隔离而不是直接进入主系统。

12. 如果发生数据越权或泄露事故，如何定位影响范围、吊销访问、通知用户并保留证据？

    **回答（生产方案）：** 立即冻结相关 token/租户和缓存，依据审计日志、trace、模型调用记录定位主体、文档和时间窗；保存不可变证据，按应急预案修复策略、轮换密钥并由安全法务决定通知。当前项目没有完整事故响应体系。

### 11.5 数据质量与知识治理

1. 企业内同一制度存在多个版本时，检索应如何优先使用最新生效版本？

   **回答（生产方案）：** 文档元数据应包含版本、状态、生效/失效时间和权威等级，默认在检索前过滤到当前生效版本；问题明确询问历史时才开放历史集合。当前 catalog 有递增 version，但没有制度生效时间和权威状态，不能完整解决业务版本冲突。

2. 已废止文档是否应该删除，还是保留并明确标记历史版本？

   **回答：** 取决于合规和业务追溯，一般保留不可变历史但从默认问答检索中排除，只有有权限的历史查询才能访问。直接删除会失去审计，继续混检又会造成错误答案。

3. 来源冲突时，如何根据权威级别、发布时间、审批状态和置信度裁决？

   **回答（生产方案）：** 先用确定性业务规则排序：已审批且生效的官方制度高于草稿，最新有效版本高于旧版；无法裁决时并列呈现来源并拒绝给唯一结论。LLM 的抽取 confidence 不能替代文档权威元数据。

4. 文档解析成功是否等于知识可用？如何监控空白页、乱码、错表格和 OCR 低质量？

   **回答：** 不等于。应记录每页字符数、OCR 置信度/语言、表格行列异常、空 Chunk 和编码替换比例，设置阈值进入人工复核；当前能拒绝整份无内容文件并记录 OCR/视觉状态，但没有完整质量看板。

5. 如何建立数据质量看板：解析成功率、空 Chunk 比例、重复率、OCR CER、孤立实体和无效引用率？

   **回答（生产方案）：** 解析和入库阶段发出结构化指标，按格式、解析器版本、租户和日期聚合；离线金标计算 CER/F1，线上监控空块、重复内容哈希、孤立实体和 citation 失败。设置趋势与突变告警，而不是只看全局平均。

6. LLM 抽取出的错误实体和关系如何由业务人员纠正？纠正结果如何防止下次重建时被覆盖？

   **回答（生产方案）：** 模型抽取层保持可重建，人工纠正写独立 override/curation 层并记录 reviewer、原因和版本；查询视图合并两层且人工优先。当前只有重建和来源删除，没有人工治理层。

7. 如何给 Chunk、Embedding、抽取 Prompt、模型和索引 Schema 做版本管理？

   **回答（生产方案）：** 在 document manifest 记录 parser/chunker、Prompt、LLM、Embedding、维度和 Schema 版本，每个派生产物带版本；升级写新索引或新图版本。当前保存文档 version 和部分模型配置快照，但还没有完整数据血缘 manifest。

8. Embedding 模型升级后，新旧向量维度不一致，如何双写、回填、验收和切流？

   **回答（生产方案）：** 新建版本化集合，新写双写，后台断点回填旧 Chunk；用固定集和 shadow 流量验收，再切读别名，观察后删除旧集合。当前 v1→v2 迁移命令体现了幂等迁移思路，但不是通用模型版本控制平台。

9. 文档更新后，已有对话和答案缓存如何感知知识版本已经变化？

   **回答（生产方案）：** 对话上下文和缓存记录引用 doc_id/version 及知识库 epoch，CDC commit 后发布失效事件；下一轮若版本不匹配就重新检索，并提示引用已更新。当前没有对话缓存和跨请求会话层。

10. 是否需要人工审核入库？哪些高风险文档或低置信度抽取必须进入人工流程？

    **回答：** 普通低风险文档可自动入库，高密级、法律财务、生效制度、解析质量低、来源冲突或抽取置信低的内容应先进入审核。审核应控制“是否对问答可见”，而不是阻塞原文件安全保存。

11. 如何让文档所有者看到“哪些问题引用了我的文档”，并处理错误反馈？

    **回答（生产方案）：** 记录经脱敏的 citation 事件和 doc_id，给 owner 提供引用次数、问题类别、反馈和版本分布；错误可触发下架、修正文档或重建。要遵守提问者权限，不能让 owner 看到未授权问题正文。

12. 如何设计答案反馈闭环，避免用户点赞率成为唯一质量指标？

    **回答（生产方案）：** 反馈同时收集是否解决、错误类型、缺失来源、过期版本和转人工结果，与规则指标和人工抽检结合。点赞受用户习惯和表达影响，不能直接当事实正确率；高风险负反馈应生成可追踪工单。

### 11.6 模型、Prompt 与 RAG 版本治理

1. LLM、Embedding、视觉模型和 Reranker 如何建立模型注册、版本冻结和回滚机制？

   **回答（生产方案）：** 建立模型注册表，记录 provider、model ID、版本/发布日期、维度、超时、价格和能力；每次发布冻结配置快照。Chat/Rerank 可按路由回滚，Embedding 需要回滚对应索引版本，不能只改环境变量。

2. Prompt 修改为什么也应该像代码一样评审、测试和版本化？

   **回答：** Prompt 会改变 QueryPlan、抽取 Schema、拒答和答案格式，本质上是系统逻辑。应进入代码审查、固定集回归、版本标记和灰度流程；本项目把 Prompt 放在代码中且有测试，但还没有独立 Prompt 注册平台。

3. 如何在不影响线上用户的情况下比较新旧检索策略或模型？

   **回答（生产方案）：** 先离线回放固定集，再用 shadow traffic 同时运行新策略但只返回旧答案；达到门槛后小比例 A/B，按用户稳定分桶。对高成本策略设预算并避免把敏感流量复制到未授权供应商。

4. A/B 测试、Shadow Traffic 和离线回放分别适用于什么阶段？

   **回答：** 离线回放适合快速可复现调参；Shadow 验证真实流量下性能和稳定性而不影响用户；A/B 才验证用户和业务指标。顺序通常是离线→Shadow→小流量 A/B→扩大灰度。

5. 模型升级后，哪些基准必须重新运行？如何设置质量回归门槛？

   **回答（生产方案）：** 至少重跑解析/多模态预检、检索、回答、引用、拒答、安全、延迟和成本基准，并按题型比较旧版。硬门槛包括业务错误、越权和引用合法性不能回退，质量变化用配对 CI 而不是只看平均。

6. 如何检测线上问题分布漂移、知识时效性下降和模型输出风格变化？

   **回答（生产方案）：** 监控问题 embedding/意图/语言分布、空召回和拒答趋势、引用文档年龄、答案长度与格式违规，和基线做漂移检测；抽样人工复核新簇。只看总 QPS 无法发现质量漂移。

7. 外部模型返回格式变化或不再支持某模型 ID 时，系统如何提前发现？

   **回答（生产方案）：** 定时运行低成本 canary 请求验证模型列表、Schema、向量维度和 Rerank 分数，供应商变更订阅配合契约测试；异常先阻止发布并切备用。当前 preflight 可手动检查，但没有定时 canary。

8. 如何防止评测集被写进 Prompt、缓存或人工调参过程，导致评测污染？

   **回答：** 开发集与保留集分开，保留集 ID/答案限制访问；QueryPlan 缓存按实验版本隔离，冻结策略后只运行一次保留集，所有实验留日志。当前 100 题经历开发调参，因此不应称为完全 held-out。

9. LLM-as-a-Judge 与被评模型来自同一模型家族时会有什么偏差？

   **回答：** 可能偏好相似表达、推理风格和答案长度，形成自我偏好。应使用不同家族裁判、答案顺序随机化、人工金标校准和规则指标交叉验证，高风险结论不能只靠单一裁判。

10. 如何为不同租户选择不同模型，同时保持 API 响应和质量指标可比较？

    **回答（生产方案）：** 用 provider adapter 统一 Pydantic 输出、usage 和错误类型，配置按租户路由；评测按模型/租户分层并保留共同锚点集。不同模型成本和质量分别报告，不把混合流量平均值当单模型结果。

11. 当新模型质量更高但成本更贵时，如何设计按问题复杂度动态路由？

    **回答（生产方案）：** 先用规则或小分类器识别简单事实、复杂多跳、高风险问题；简单题用小模型或抽取，高风险/复杂题升级大模型。路由器也要在固定集评测误分成本，并允许超时和预算降级。

12. 如何设置模型输出内容安全策略，同时避免误伤正常企业术语？

    **回答（生产方案）：** 使用租户可配置的分类策略、上下文敏感检测和人工申诉，不只靠关键词黑名单；安全拦截与业务拒答原因分开记录。企业术语白名单必须经过审核，不能由用户提示临时绕过。

### 11.7 发布、变更与可观测性

1. 从本地 Docker Compose 迁移到 Kubernetes，需要拆分哪些 Deployment、StatefulSet、Job 和 CronJob？

   **回答（生产方案）：** API/Query、解析 Worker、Embedding/抽取 Worker 和 CDC Consumer 做独立 Deployment；Kafka/Neo4j/向量库优先用托管服务或 Operator 管理 StatefulSet；迁移、回填、重建做 Job，质量扫描和备份做 CronJob。SQLite 替换为共享数据库。

2. 服务如何配置 readiness、liveness、startup probe 和优雅退出？

   **回答（现有基础+生产方案）：** 当前已有 live/ready；K8s 中 startup 等初始化和索引连接，readiness 控制接流量，liveness 只检测死锁/进程。优雅退出先停止接流量、停止拉 Kafka、等待正在处理任务或释放租约，再关闭模型客户端和数据库连接。

3. 数据库 Schema、Chroma 集合和 Neo4j 图模型变更如何做到向前兼容与可回滚？

   **回答（生产方案）：** 使用 expand-and-contract：先增加新字段/新集合并双读写，回填验证后切读，最后删除旧结构；每次迁移幂等且记录版本。当前 v2 集合保留 legacy 读取就是该思路的简化实现。

4. 为什么应用回滚容易，但已经写入的新格式数据回滚更困难？

   **回答：** 旧代码可能不认识新字段、向量维度或图关系，且数据变更不可通过换镜像自动撤销。发布前要保证旧代码能读新写数据，或使用版本化存储和双写；破坏性迁移必须最后执行。

5. 如何进行滚动发布、蓝绿发布或金丝雀发布？什么指标触发自动回滚？

   **回答（生产方案）：** 无 Schema 变化可滚动，有高风险模型/数据变化优先金丝雀或蓝绿；按租户/用户稳定分流。业务错误、p95、非法引用、越权、安全拦截、空召回和成本超过阈值自动回滚，而不是只看 Pod 健康。

6. 一次问答跨越多个 Agent 和外部服务，如何通过 trace_id 串联日志、指标和调用链？

   **回答（生产方案）：** 网关生成 trace_id，LangGraph state、HTTP header、数据库/Kafka metadata 和模型调用都传播它；OpenTelemetry 记录 span 和阶段耗时。当前 thread_id 与高层 trace 能定位单流程，但还没有分布式追踪后端。

7. 线上最关键的 RED / USE 指标分别是什么？

   **回答：** RED 看请求 Rate、Error、Duration；USE 看各资源 Utilization、Saturation、Errors。对本项目还要加 Kafka lag、模型 429、向量/图查询 p95、线程池/连接池饱和和 OCR 队列长度。

8. 除 CPU、内存外，为什么还要监控空召回率、拒答率、Citation 有效率和 Rerank fallback？

   **回答：** 服务可能资源正常但答案质量已经退化，例如索引漏写会导致空召回、模型格式变化导致非法引用。业务质量指标能比 CPU 更早发现这类“绿色但不可用”的故障。

9. 告警阈值如何避免过于敏感导致告警风暴，或过于迟钝漏掉事故？

   **回答（生产方案）：** 基于 SLO 错误预算和多窗口 burn rate，要求持续时间与最小样本数，并做依赖告警聚合；分 warning/page 两级。发布期可用相对基线告警，避免夜间低流量单个错误触发全员。

10. 如何制定 Runbook：模型超时、Kafka 积压、Neo4j 慢查询、向量索引损坏分别怎么处理？

    **回答（生产方案）：** 每个 Runbook 包含症状、看板、确认命令、降级开关、止损、恢复、数据校验和升级联系人。模型超时切备用/熔断，Kafka lag 扩消费者并查毒消息，Neo4j 用 PROFILE/限跳，索引损坏切旧版本并从 manifest 重建。

11. 如何在生产环境调试单个失败请求，同时避免日志记录敏感正文？

    **回答（生产方案）：** 用 trace_id、阶段、模型/Prompt版本、doc/chunk 哈希、长度和错误类型重放；需要正文时走受审批的短期安全采样并脱敏。默认日志不保存完整问题、证据和模型 header。

12. 发生线上事故后，复盘应该包含哪些数据，而不是只写“增加重试”？

    **回答：** 包含时间线、影响租户/请求、SLO与数据影响、检测和处置、技术与流程根因、为何防线失效、短长期行动项及负责人/期限。盲目加重试可能放大事故，必须说明容量和幂等依据。

### 11.8 成本控制与业务指标

1. 如何计算每份文档入库成本和每次问答成本？需要统计哪些 token 与基础设施资源？

   **回答（生产方案）：** 入库统计 OCR/视觉、文本/VL Embedding、每 Chunk 抽取 token、存储与 CPU；问答统计计划、两类 Embedding、Rerank、时间/生成 token、缓存命中和数据库耗时。按 provider 当时单价和租户汇总，当前已有部分调用/token 统计但未形成完整成本账单。

2. 生成、知识抽取、视觉理解、Embedding 和 Rerank 中，哪个通常是主要成本项？如何用账单验证？

   **回答：** 通常逐 Chunk 抽取和答案生成 token 较高，图片多时视觉也可能占主导，但不能凭通常下结论。把 usage 与 provider 账单按 request/job 对账，计算各阶段占比和 p95 才能确定优化优先级。

3. 如果要求总成本降低 30%，为什么应先做调用分层和缓存，而不是直接换最便宜模型？

   **回答：** 缓存、去重和按难度路由能消除不必要调用，通常质量损失更可控；直接换小模型可能降低 QueryPlan、抽取和引用质量，反而增加重试。每项降本都要在固定集和线上灰度中验证。

4. 哪些结果可以安全缓存：查询向量、QueryPlan、检索结果、Rerank 结果还是最终答案？

   **回答（生产方案）：** 查询向量和稳定 QueryPlan 最容易缓存；检索/Rerank 缓存必须带知识版本、权限和策略；最终答案风险最高，只适合低风险热点且绑定相同权限与证据版本。敏感原文不得进入不安全共享缓存。

5. 知识更新后如何精确失效缓存，避免全量清空造成缓存雪崩？

   **回答（生产方案）：** 缓存记录依赖 doc_id/version 或 namespace epoch，CDC commit 发布失效事件；精确删除相关键，无法追踪时提升租户 epoch 让旧键自然过期。加随机 TTL、防击穿锁和预热避免同时回源。

6. 如何根据问题复杂度决定是否启用 Graph、Reranker、视觉模型和大参数 LLM？

   **回答（生产方案）：** QueryPlan/轻量分类器识别实体关系、多跳、图片需求和风险等级：简单事实走 Vector+小模型，关系多跳启用 Graph，候选模糊启用 Rerank，只有引用图片时才用视觉，大模型处理复杂/高风险。路由决策要记录并做分桶评测。

7. 如何设置每租户预算、速率限制、并发限制和月度用量告警？

   **回答（生产方案）：** 网关和模型代理按 tenant 维护 token bucket、并发 semaphore、日/月 token 与金额额度，接近阈值告警；超额可降级或等待审批。高优先级业务与批处理使用不同配额，避免一个租户耗尽全局资源。

8. 系统技术指标提升，为什么不一定带来业务价值？

   **回答：** Recall 提升可能增加噪声、延迟和成本，也可能用户根本不采纳答案；本项目 Hybrid 检索提升但 EM 下降就是例子。最终要看自助解决率、找资料时间、错误成本和用户信任，并守住安全边界。

9. 企业知识库应关注哪些业务指标：自助解决率、平均找资料时间、转人工率、引用点击率还是用户采纳率？

   **回答：** 这些都应结合：自助解决率和时间反映效率，转人工和追问反映不足，引用点击/采纳反映信任；还要监控错误纠正率和高风险误答。不能只优化点击率，否则可能鼓励冗长或猎奇答案。

10. 如何评估错误回答的业务损失，并据此设置拒答阈值？

    **回答（生产方案）：** 按场景建立成本矩阵，比较误答、拒答和转人工代价；法律财务误答成本远高于普通搜索，因此阈值更保守。用带业务权重的验证集选择阈值，并定期复核真实事故和反馈。

11. 高价值但低频的问题，是否应该与高频简单问题使用相同优化目标？

    **回答：** 不应该。高价值问题更重正确性、完整引用和人工升级，高频简单题更重延迟和成本；应分层 SLO、模型路由和评测权重，而不是用一个平均 EM 覆盖全部业务。

12. 如何向业务方解释“提高拒答率可能提升系统可信度”？

    **回答：** 拒答不是目标本身，而是在证据不足时用一次可恢复的转人工，换取减少高成本误答。要同时展示误答率、正确拒答率和自助解决率，找到业务成本最小点，不能靠一味多拒答刷 Rejection F1。

## 十二、现场画图或手写代码题

1. 画出 4-Agent 总体架构与三条 LangGraph 数据流。

   **回答要点：** 我会先画 FastAPI/Watchdog 接入、Supervisor 与 ingest/qa/update 三个子图、解析/抽取/问答/更新四个职责 Agent，再画 SQLite、Chroma、Neo4j、Kafka。三条流分别突出 Chunk Diff、Vector/Graph 并行+RRF/Rerank、Kafka 幂等+verify/repair；详细图可直接参考 [architecture.md](architecture.md)。

2. 手写加权 RRF 公式，并说明重复文档如何累积分数。

   **回答：** `RRF(d)=Σ_i w_i/(k+rank_i(d))`，本项目 `k=60`。同一 chunk 在 Vector 和 Graph 中出现就累加两路贡献；同一路先按 chunk_id 去重，v2 与 legacy 同时存在时也过滤重复，最后再归一化到 0–1 用于展示。

3. 写一个稳定 chunk_id 的生成函数，并解释分块漂移问题。

   **回答：** 伪代码是 `hash(doc_id + unit_id + sha256(normalize(content)) + occurrence)[:32]`。它不依赖全局序号，所以其他章节变化不影响本 unit；但长 unit 前部插入会改变滑窗边界，使后续块内容哈希变化，进一步可用句子锚点或内容定义分块缓解。

4. 写 added / changed / deleted / unchanged 的 diff 伪代码。

   **回答：** 当前实现是 `added=new_ids-old_ids`、`deleted=old_ids-new_ids`、`unchanged=old_ids&new_ids`；内容变化因 ID 含 content_hash，表现为 deleted+added。若需要显式 changed，要另按稳定位置 key 对齐，再比较 content_hash，不能只看 chunk_id。

5. 写一个 Kafka 事件幂等消费流程。

   **回答：** 先用 event_id 查询 SQLite；COMMITTED 直接提交 offset，APPLYING 不重复执行，FAILED 且 attempts<3 原子 claim 为 APPLYING；执行幂等 upsert/delete，verify 成功写 COMMITTED 再提交 offset，失败写 FAILED 并退避，超过次数送 DLQ。当前项目除 DLQ 外基本按此实现。

6. 写一个只允许白名单查询模板的参数化 Cypher 示例。

   **回答：** 例如模板固定为 `MATCH (e:Entity {key:$key})-[:MENTIONED_IN]->(c:Chunk) WHERE c.doc_id IN $doc_ids RETURN c LIMIT $limit`，`key/doc_ids/limit` 作为参数传入；跳数由代码从 1–3 模板中选择。绝不把 LLM 返回的实体、predicate 或整段 Cypher字符串拼接执行。

7. 写一个 Citation Validator，验证 doc_id、chunk_id 和 quote 是否匹配。

   **回答：** 先用本次授权后召回上下文建立 `chunk_id -> context` 白名单；逐 citation 检查 ID 存在、doc_id 一致、quote 是规范化 context 内容的子串且用户仍有 ACL；去重后若 answerable 但无合法引用，强制拒答。当前实现完成 ID/doc 绑定和固定 quote，句级 quote 子串校验可进一步增强。

8. 写一个有最大次数、指数退避和可重试错误白名单的异步重试器。

   **回答：** 循环 `max_attempts`，捕获 408/429/5xx、timeout、transport error 才重试，等待 `min(cap, base*2^attempt)+jitter`；其他异常立即抛出，最后保留原异常。当前 Reranker 符合白名单思路，但通用 LangGraph 重试还需收窄异常类型并加入 jitter。

9. 写一个受限计算器，说明为什么不能直接执行 LLM 生成的表达式。

   **回答：** 用 AST 解析表达式，只允许数字、`+ - * /`、一元正负和括号，限制节点数、数值范围并拒绝除零，不能调用 `eval`。LLM 输出可能包含函数、属性访问或代码注入；本项目 `safe_calculate` 用白名单 AST 验证计算式。

10. 设计一次 Vector / Graph / Hybrid / Hybrid+Rerank 的公平消融实验。

    **回答：** 固定文档、Chunk、问题、QueryPlan、Top-K、生成模型、Prompt和随机种子，仅逐步打开 Graph 和 Rerank；按同一 sample_id 配对报告 Recall/All-hit、EM/F1、Citation、延迟、token 和 fallback，并做 bootstrap CI。Graph-only 用于诊断，最终还要按题型分层，失败样本不能删除。

## 十三、最危险的真实性追问

这些问题必须按仓库真实结果回答，不能用计划目标代替实测结果。

1. **“你简历上说检索准确率提升了多少，准确率具体是哪一个指标？”**

   **回答（实测）：** 我不会笼统说“检索准确率”。当前可复述的是 All-evidence Hit@10 从 Vector 的 45.33% 到 Hybrid 的 50.67%，提升 5.34 个百分点；Evidence Recall@10 从 74.44% 到 76.78%。

2. **“50.67% 是回答准确率吗？”**

   **回答（实测）：** 不是，它是 Top10 是否找齐全部标准证据文档的比例。Hybrid 的严格 Answer EM 是 57.33%，必须分开表述。

3. **“为什么 Hybrid 的检索指标提升了，Answer EM 却从 60.00% 降到 57.33%？”**

   **回答（实测分析）：** 图分支补到了证据，也引入了噪声；精排/证据打包未必把新增证据正确传给生成器，通用 ComparisonTool 还因槽位约束过度拒答。我据此默认关闭了该工具，但尚未用同一 100 题证明回滚后的新 EM，所以不宣称已经修好指标。

4. **“这个提升的 95% 置信区间是否跨 0？统计上显著吗？”**

   **回答（实测）：** 当前明确报告的配对 Answer EM 差值区间是 `[-10.67, 5.33]` 个百分点，跨 0，不显著。检索提升也应结合其配对区间和样本范围解释，不能只看点估计。

5. **“你是否真的验证了 1000 篇或千级文档的实时问答？”**

   **回答（实际边界）：** 没有。当前是固定 100 篇 MultiHop-RAG 子集和本地 Docker 验证，没有千级生产规模压测，因此简历不写“支持千级文档实时问答”。

6. **“CDC 更新效率提升 95% 是实测还是原仓库宣传数字？”**

   **回答（实际边界）：** 不是本项目实测结果。代码实现了稳定 Chunk Diff、幂等和修复，数据集也准备了 AKH-CDC-300，但完整增量/全量性能对照尚未完成，所以我不会使用 95%。

7. **“公开数据集能代表企业线上问题吗？你的结论外推范围是什么？”**

   **回答：** 不能完全代表。它用于可复现地验证跨文档检索和问答，结论只适用于当前固定样本、模型和参数；企业上线还需加入脱敏真实日志、ACL、版本冲突、内部缩写、表格和长文档集。

8. **“4 个 Agent 中有几个是真正自主决策的 Agent？”**

   **回答：** 没有让四个 Agent 自由协商或自主递归调用。语义决策主要在 QueryPlan 和 LLM 抽取/生成，整体由确定性 Supervisor 和固定 DAG 控制；因此更准确的说法是“4 个 Agent 职责模块的 LangGraph 编排”，而不是开放式自治群体。

9. **“所谓 11 类文档，是 11 个独立解析器还是格式族统计？”**

   **回答：** 是 11 个格式族，底层有共享实现：Excel/CSV 都是 table 类型，PNG/JPG 共享 image 管道，JSON/JSONL 共享结构遍历。它不是为了凑数的 11 个完全独立模型，而是 11 类输入能力。

10. **“视觉能力与 VL Embedding 是否都做过真实 API 验证，还是只有 Fake 测试？”**

    **回答（实测）：** 两者都做过一次真实最小预检：视觉描述成功返回 401 字符，图片和文本 VL Embedding 均为 1024 维，共 2 calls/42 input tokens；自动化测试则主要用 Fake。预检证明接口和契约可用，不证明大规模视觉质量。

11. **“为什么项目可以展示为完整 MVP，但还不能称为生产级系统？”**

    **回答：** MVP 的业务闭环、真实存储、三条流程、安全校验、测试和评测都可运行；但生产级还要求认证/租户、权限前置过滤、对象存储、分布式任务、高可用、备份灾备、SLO 监控、DLQ 和真实规模压测。当前这些大多只是设计方案。

回答这些问题时应主动说明：

- 100 题配对实验中，Vector / Hybrid 的 **Evidence Recall@10 为 74.44% / 76.78%**；
- Vector / Hybrid 的 **All-evidence Hit@10 为 45.33% / 50.67%**，提升 **5.34 个百分点**；
- Vector / Hybrid 的 **Answer EM 为 60.00% / 57.33%**，生成端没有获得正提升；
- 这证明了当前图增强对“找齐多跳证据”有帮助，但还不能宣称整体问答准确率提升；
- 未进行的规模、延迟和 CDC 性能实验必须明确说“尚未实测”。
