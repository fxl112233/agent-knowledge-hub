# AgentKnowledgeHub 面试讲解

## 60 秒项目介绍

我独立实现了一个面向企业文档的 4-Agent 知识管理系统。四个 Agent 分别负责文档解析、知识抽取、智能问答和知识更新，由一个 Supervisor 按 ingest、qa、update 三条 LangGraph 子图调度。系统支持 11 类文档格式，文本、表格和原始图片分别进入 Chroma 集合，Neo4j 保存带来源的实体关系，问答时并行做多模态向量召回和 1–3 跳图检索，再通过严格加权 RRF、BGE 两级精排和文档内二次检索生成带真实 Chunk 引用的答案。更新侧使用 Watchdog/API、Kafka、稳定 Chunk ID 和幂等事件，只处理变化块。

我还建立了固定数据、分层抽样、断点续跑和配对 bootstrap 的评测链路。100 题实验中，Hybrid 的 All-evidence Hit@10 从 45.33% 提升到 50.67%，但 Answer EM 从 60.00% 降到 57.33%。我没有把检索提升包装成回答准确率，而是定位到比较工具过度拒答并将它默认关闭。

## 为什么要拆 4 个 Agent

我不会按“步骤数量”机械拆 Agent，而是看四个条件：输入输出契约是否独立、是否需要不同工具、失败补偿是否不同、是否需要单独扩缩容或观测。解析、抽取、问答、更新正好满足这些条件。

拆得太多会产生状态序列化、上下文丢失、模型调用和错误传播成本，也更容易出现循环和职责重叠。所以文档校验、分块、RRF、日期比较、哈希 diff 仍是普通确定性节点，不为了叫 Multi-Agent 就全部包装成 LLM Agent。

## 调度器怎么实现，怎么避免踢皮球

Supervisor 只做白名单路由，不做无限制中心化规划：请求显式进入 ingest、qa 或 update 子图。每条子图是固定 DAG，条件边只能跳到预定义节点；普通阶段最多重试 2 次，CDC 最多 3 次；状态记录阶段和错误类型，Checkpoint 支持恢复。没有 Agent 可以任意调用另一个 Agent，所以不存在互相转交任务形成无限循环。

## 两个 Agent 结论矛盾时以谁为准

项目不使用“投票决定事实”。向量和图检索冲突时，它们只是两个候选来源，统一经过 RRF、Reranker 和来源校验；最终 citation 必须指向真实 Chunk。跨存储更新则以 SQLite 已提交版本和 Chunk 集合为预期状态，分别与 Chroma、Neo4j 对比，不一致就进入 repair。也就是由可验证的数据约束仲裁，而不是由某个 Agent 权威更高。

## 为什么 RAG 能缓解幻觉，有什么局限

RAG 把回答从模型参数记忆改成“在外部证据约束下生成”，引用校验又把答案绑定到真实 Chunk，因此能降低无来源编造。但它不能保证正确：召回遗漏、检索噪声、文档本身错误、版本冲突、分块切断关系、模型误读证据都会产生错误。本项目的实验正说明，检索证据更完整不等于 Answer EM 一定更高。

RAG 会在以下情况拉低效果：问题本来是通用常识却注入大量相似文档；库中存在互相冲突的旧版本；Top-K 太大导致注意力稀释；表格被错误线性化；强行图扩展引入只有实体共现、没有答案价值的邻居。处理方式包括 metadata 过滤、版本优先级、精排、多样性约束、证据槽位和不足时拒答。

## 长上下文会取代 RAG 吗

不会完全取代。长上下文适合文档数量少、一次性分析、需要保持全局结构的任务；RAG 适合语料持续变化、需要权限过滤、低 token 成本、可追溯引用和跨大量文档检索的系统。实际工程会组合：先检索到文档或章节，再把较长的局部上下文交给模型。

## RAG 还是微调

知识经常变化、回答必须引用内部事实时优先 RAG；要改变输出格式、语气、工具调用习惯或稳定学习任务模式时考虑微调。企业制度、合同和项目资料属于外部可更新知识，因此本项目首先用 RAG。两者并不互斥：可以微调模型的行为，再由 RAG提供最新事实。

## 超长 PDF 如何入库

上传只负责落盘和创建任务，1000 页 PDF 不应同步阻塞 HTTP。后台按页解析；数字页提取文本和表格，低文本页渲染后 OCR，图片保存为 SHA-256 受管资产。随后按章节和约 500 token/80 overlap 分块，分批 Embedding、抽取和写库，并逐阶段记录进度。失败时从 Checkpoint 恢复，不从第 1 页重跑。为提升长文档召回，可建立“文档—章节—Chunk”层级索引，先选文档/章节，再在文档内二次检索。

当前 MVP 的同步上传接口适合普通文件；要声称真正支持 1000 页生产文档，还需要增加对象存储、异步任务 API、分布式 worker、页级进度和专项压测。这一点面试时应主动区分“设计方案”和“当前实测能力”。

## 测试集如何避免自嗨

测试集分三层：公开数据用于可比性，固定分层样本用于快速开发门控，真实业务日志去标识后用于线上回归。公开数据记录 URL、版本、许可证、SHA-256 和固定样本 ID；开发集和保留集分开，不能因为指标低就删除失败题。所有策略用同一问题、QueryPlan、Top-K 和模型做配对对照，并报告置信区间和失败案例。

本项目当前正式可讲的是 MultiHop-RAG 固定 100 题配对实验。它覆盖比较、推断、时间和无答案，但不等于真实企业流量；如果上线，还需要补充权限问题、版本冲突、表格查询、长文档和用户追问日志。

## 自动化指标与人工评估

检索看 Recall@10、All-evidence Hit@10 和 Precision；短答案看 EM、Token F1；引用看 Citation Precision/Recall；无答案看 Rejection F1；工程看错误率、p50/p95、调用数和 token。LLM-as-a-Judge 可评价完整性、忠实度和表达，但没有一个固定的“打分准确率”，它随领域、提示词和基准模型变化，必须先用人工标注集测一致率。

以下情况必须人工复核：法律/财务等高风险答案；开放式答案没有唯一标准；模型裁判与规则指标冲突；策略差异小于置信区间；出现新错误类型或版本冲突；准备写入简历或对外报告的代表性案例。实践中可对全量做规则指标和 LLM 初筛，再对所有失败、所有分歧和随机 10%–20% 样本双人复核。

## 为什么使用 Recall@10

标准答案不是 10 篇证据。MultiHop-RAG 每题通常需要 2–4 篇跨文档证据，`@10` 表示系统允许返回最多 10 个候选，再检查标准证据是否在其中。K 太小会对多跳问题过严，K 太大又会掩盖噪声并增加生成成本，所以同时报告 Recall@10、All-evidence Hit@10 和 Precision@10。

## 如何解释当前实验结果

我的结果是 Hybrid 提高检索完整性，但没有提高最终 Answer EM。v5 中 Vector/Hybrid 的 All-evidence Hit@10 分别是 45.33% 和 50.67%，说明图候选对跨文档证据有帮助；Answer EM 却是 60.00% 和 57.33%，配对差值的 95% CI 跨过 0，不能声称显著提升。

我进一步发现通用 ComparisonTool 过度保守：一部分题已经完整召回证据，却因为槽位约束返回不可回答。因此最终默认关闭它，保留语义明确的时间工具。这体现了检索、推理、输出契约必须分层评估，而不是只调一个总分。

## 10 万 DAU、日均 5 问、p95 2 秒怎么设计

这是目标生产架构，不是当前单机实测能力。平均约 5.8 QPS，但要按早高峰和突发容量设计到几十至上百 QPS：API Gateway 做认证、租户与限流；Query 服务无状态水平扩容；Embedding、向量检索、图检索并行；Redis 缓存查询向量、检索结果和热点答案；生成模型使用独立推理网关、流式返回和超时降级；文档解析、抽取和 CDC 全部走 Kafka 异步 worker；对象存储保存原文；监控拆分检索、排队、首 token 和完整生成延迟。

如果“完整答案 p95 2 秒”是硬约束，云端大模型通常不可控。我会把 2 秒定义成首 token 或检索完成 SLA，设置 300–500 ms 检索预算，超时关闭图扩展/二次检索并退化为向量链路；完整答案使用流式响应并另报结束延迟。

## 多租户物理隔离

物理隔离不是只加 `tenant_id`。高要求租户使用独立对象存储 bucket/加密密钥、独立 Chroma/向量索引、独立 Neo4j database、独立 SQLite/关系库 schema 和 Kafka topic/ACL；控制面保存租户到资源的映射。API 从签名身份解析 tenant，服务端注入作用域，永远不接受客户端自由传租户过滤条件。共享计算层可以复用，但数据面和密钥要隔离。

## 高峰 3 倍流量如何防雪崩

入口限流和租户配额先挡住过载；队列削峰，查询服务按队列长度和 p95 自动扩容；热点缓存减少 Embedding 和生成；向量/图/模型分别设并发池、超时、熔断和 bulkhead，避免一个依赖拖垮全链路；低优先级请求降级为 Vector-only、减小候选数或返回稍后重试。重试必须指数退避并带 jitter，且只对幂等操作执行，避免重试风暴。

## 推理成本降低 30% 先动哪里

先从可观测数据判断成本分布，通常生成模型输入 token 是最大项。优先级是：缓存相同/近似问题；减少 QueryPlan 和答案的重复调用；用 Reranker 与文档内检索压缩上下文；简单事实题用小模型或直接证据抽取；时间和数值题走确定性工具；限制输出长度；批量和缓存 Embedding。不能只把模型换小而不测质量，所有降本策略都要在固定集上守住 Recall、EM、引用和拒答指标。

## 项目目前不是生产系统的地方

当前是工程完整的 MVP，不是玩具脚本，但也不是已经承载真实企业流量的生产系统。它具备真实存储、并行检索、幂等 CDC、恢复、测试和可复现评测；缺少多租户认证、对象存储、任务队列扩缩容、SLO 监控、灾备和真实流量压测。最好的表述是“具备生产化设计意识的可运行 MVP”，不要冒充线上业绩。
